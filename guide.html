XX-PRD

需求分析与原型设计工作台 · Skill 说明指南

把「一句话想法 / 模糊需求 / Vibe-Coding Demo」收敛成 可交互原型 + EARS 规范 PRD + 标注对齐 三合一的单文件 HTML 容器； 基于 Ant Design 5 做设计（容器内置压缩版 AntD token 与组件语义）， 并据此产出可直接交给 AI 开工的开发交接包。 画页面前先做行为建模 —— 定清「谁在什么状态下能做什么」，按钮可用性与页面切分都是它的推论，不是审美选择。 本文是 skill 的自解释文档 —— 讲清它怎么跑、遵从哪些设计原则、产出什么结构、产物怎么用。

1工作流

从「用户开口」到「可交付 PRD」，走八个阶段。两个关键位置设了人工确认卡点 —— 卡点未确认不往下走， 这是本 skill 与「一口气生成一份文档」最大的区别：需求与板块是产研对齐的锚，锚歪了后面全是返工。 在需求与画页面之间，多插了一道行为建模：先把「谁在什么状态下能做什么」定下来，再决定按钮长什么样、页面怎么切。

八阶段与两个卡点

需求澄清
9 维度提问，每轮 5~7 问；产出 4 份 shaping 文档
STAGE 02
需求分析 EARS
逐条 EARS 条目 + 状态机 + 质量门禁
STAGE 03
行为建模
业务任务 → 命令策略（角色×状态×动作）→ 页面职责契约
卡点 A
确认需求与行为
需求清单 + 状态机 + 命令策略表 + 页面职责表
STAGE 04
板块计划
按模块/页面拆板块，写 boardPlan
卡点 B
确认板块
顺序 + 颗粒度
STAGE 05
逐板块生成
原型 + PRD 同步产出，每批 1~2 个板块
STAGE 06
标注评审迭代
用户在原型上打标注 → AI 按指令改
STAGE 07

PRD + 导出
组装完整 PRD、跑校验、出交接包
i

卡点是停下来等用户确认，不是「自动跳过」。卡点 A 确认需求语义与命令策略（这个状态下这个按钮该不该可点）， 卡点 B 确认工作颗粒度 —— 两次确认把返工挡在生成之前。原型定稿不再单设卡点，改为阶段⑦里的状态走查： 把单据状态挨个切一遍，看按钮该亮的亮、该灰的灰、该消失的消失。

!

为什么行为建模要单独一个阶段：只做 EARS + 状态机，信息是分开记录的 —— 角色在 users、状态在 stateMachines、按钮在 componentTree， 三者之间没有任何强制对应关系。于是「审批中」的单据照样摆着一个能点的「提交审批」按钮， 而页面 goal 只有一句话，回答不了「这几个表单为什么属于同一个页面」。 阶段③ 的工作就是把这些散点连成一条链：角色 → 任务 → 命令 → 前置条件 → 状态转移 → 页面职责 → 组件。

规则 2

规则 3

逆向结果再回到 ① 澄清流程与用户对齐 —— 代码是「压缩的 PRD」，本 skill 的工作就是把它展开。详见 references/06-demo-reverse.md。

2设计准则

这个 skill 不自己发明设计语言 —— 它基于 Ant Design 5 做设计：颜色、间距、圆角、字号、组件形态 全部直接复用 AntD 的 token 与组件语义，容器内置一套压缩版 AntD 5 实现，不引 CDN、不引图标库。 在这条基线上推导出 7 条可执行的设计原则（2.2），再把原则落到四个具体维度 —— 容器选型、主子表、跳转关系、画布与视觉。

i

换句话说：「容器选型」「主子表」这些不是并列的另一套规矩，而是 7 条原则推导出来的结果。 所以它们能被校验器检查、能被容器运行期兜底，而不是靠评审时「记得要这样做」。

2.1 设计基线 · 为什么是 Ant Design 5

先回答一个前提问题：这个 skill 生成的原型，视觉与交互从哪里来？答案是整套继承 AntD，而不是自由发挥。

Token 直接复用

容器内置 --ant-primary:#1677ff 等一整套变量，取值与 AntD 5 官方 token 一致。 原型与真实中后台同色同形，评审时不会被「配色不像我们的系统」打断。

组件语义一一对应

68 个白名单组件全部对应 AntD 真实组件（Table / Form / Descriptions / Timeline / Steps / Tabs …）。 原型里看到的每个控件，在实现阶段都能落到同名 AntD 组件，不存在「原型有、实现没有」的落差。

交互反馈成套继承

hover / active / disabled / loading / 选中 / 空态 / 告警，全部按 AntD 默认行为实现。 PRD 里因此不需要逐条写「按钮按下要变深」这类无效描述。

信息密度即行业默认

32px 控件高、14px 正文、6px 圆角、8px 卡片圆角 —— 这就是 B2B 中后台的默认密度。 skill 不为「更紧凑 / 更炫」做二次设计，密度本身就是共识。

记

产物不是「像 AntD 的示意图」，而是直接跑在 AntD token 与组件语义上的可交互原型 —— 这也是它能把原型直接转成开发交接包的前提。

2.2 七条设计原则

AntD 的四大设计价值观（自然 / 确定 / 意义 / 生长）与十条设计原则，在这个 skill 里被收敛成 7 条可执行原则：每一条都能指到容器里的一段实现、或校验器里的一条规则 —— 不是写在文档里的口号。

P1 自然 Nature

交互隐喻贴合物理直觉与用户预期。

AntD 价值观「自然」· 原则「提供邀请 / 巧用过渡」

落实：抽屉从右侧滑出、对话框居中 + 遮罩、滚轮缩放以光标为锚点（不是画布中心）、 拖拽平移跟手、子表在主表下方（视觉上从属）。

P2 确定 Certainty

相同语义永远用相同组件、相同颜色、相同容器。

AntD 价值观「确定」· 原则「重复」

落实：四态固定映射 success / warning / error / processing； 按钮层级固定 primary(主) / default(次) / danger(危险) / text(轻)； 容器选型有唯一决策树 —— 同一场景在任何页面都得到同一结果。

P3 意义 Meaning

信息分层靠字号、颜色、间距，不靠装饰。

AntD 价值观「意义」· 原则「对比」

落实：文字四档色（.88 / .65 / .45 / .25）+ 字号三档（16 / 14 / 12）； 两级阴影只给「卡片」与「浮层」；不引入渐变、发光、拟物 —— 中后台的第一诉求是扫读效率。

P4 亲密性 Proximity

相关的靠拢成组，无关的拉开距离。

AntD 原则「亲密性 / 对齐」

落实：表单按业务分组、Descriptions 成对排列、列表页把「查询条 / 操作条 / 表格 / 分页脚」 垂直贴合成一体。主子表就是这么来的 —— 主表与子表必须共享选中态、贴合在同一容器里， 而不是平铺成两个兄弟模块（见 2.4）。

P5 直截了当 Straightforward

减少一次操作所需的跳转与步骤。

AntD 原则「直截了当 / 足不出户」

落实：列表页三件套同屏（查询 / 操作 / 分页不跳页）；抽屉承载编辑（保留父页上下文）、 对话框承载强模态确认、只有「复杂长程 / 需独立 URL / 需长期停留」才升级新页面。 容器选型就是这么来的（见 2.3）。

P6 即时反应 Instant Feedback

每个操作都有可见结果，状态永远不藏在系统里。

AntD 原则「即时反应 / 提供邀请」

落实：主表选中行浅蓝高亮 + 单选圆点点亮；操作列按钮不误触发选行；分页脚显示「共 N 条」； 子表标题显示「· 共 N 条」；bind/bindTo 匹配不到时容器运行期告警 —— 把「静默失败」变成「可见告警」。

P7 可生长 Growth

结构可扩展，产物可被机器消费。

AntD 价值观「生长」· 原则「简化交互」

落实：渲染器注册表 R.<Type> 可扩展（加组件不改引擎）； 组件白名单由校验器守门；一份 JSON 同时产出人看的原型和 AI 看的开发交接包 （devspec.json / AGENT.md）—— 原型与文档不会漂移。

原则 → 场景准则：四个维度分别推导自哪一条

2.3 容器选型（对话框 / 抽屉 / 新页面）

这是 P5 直截了当与 P6 即时反应在容器维度的应用：能用「并排」解决的就不「进入」， 能用「打断」解决的就不「并排」—— 三种容器的本质定位完全不同，混用是 B2B 最常见的体验债。

打断式 · 强模态

对话框 Dialog

完全脱离上下文，处理完即回。宽度 400–560px。
用于：轻量确认、危险操作、≤3 字段快速编辑。

并排式 · 半模态

抽屉 Drawer

保留父页上下文，侧边滑出。480–720px。
用于：多字段编辑、详情主从、边看边操作。

进入式 · 无模态

新页面 Page

整屏切换、独立 URL。
用于：复杂长程表单、详情工作台、多步向导。

记

一句话：对话框是「打断」，抽屉是「并排」，新页面是「进入」。

决策树（按顺序判断，命中即停）

Q1 · 内容是否轻量、且需要快速返回？
是对话框 —— ≤3 字段 / 纯确认 / 强耦合原流程
否进入 Q2
Q2 · 是否需要对照父页面，且内容中等？
是抽屉 —— 多字段单屏 / 详情主从 / 边看边操作
否新页面 —— 复杂、多步、需独立 URL、需长期停留

拿不准时问自己三个问题：要不要回头看原来的列表？（要 → 抽屉） 会不会在这里待很久？（会 → 新页面） 是不是只想点个确认？（是 → 对话框）

B2B 特有准则

  1. 详情主从首选抽屉，别用对话框 —— 对话框展不开关联信息与操作区。
  2. 禁止对话框套对话框（dialogception）：第二层一律改用抽屉或新页面。
  3. 长表单（>15 字段）禁用对话框：滚动、校验、键盘体验都会崩。
  4. 需要全屏专注的复杂编辑用新页面，抽屉的半屏会限制信息密度。
  5. 危险操作 / 批量确认用对话框：利用强模态强制用户确认。
  6. 状态保持：抽屉关闭保留父页筛选/页码/滚动；新页面要支持草稿保存 + 未提交离开提示；弹窗/抽屉默认丢弃未保存。
  7. 抽屉方向：右滑用于详情 / 编辑，左滑常用于筛选面板或导航。
  8. 抽屉里塞 ≥3 个 tab 的工作台要升级为新页面。

2.4 主子表（单页数据层级多时）

这是 P4 亲密性与 P6 即时反应在数据层级维度的应用：主记录与它的明细在业务上是一体， 视觉与交互上就必须贴合在一起、共享选中态。 判断标准：同一条主记录下挂着若干明细，且用户需要边扫主表、边看某一条的明细。 典型场景：一条巡检任务 → 若干巡检项；一张订单 → 若干商品行；一台设备 → 若干保养记录。

!

不要把两张表平铺成兄弟节点 —— 那样点上行、下行不会动，用户会以为页面卡了。 必须用 MasterDetail 把两张表包起来做联动。

结构约定

位置要求
children[0]主表 Table：props.radio: true 显示单选圆点标出当前行；不要设 props.rowClick（点行 = 选中行，校验器会 ERROR）
children[1]子表 Table：data 写全量明细，容器按 bind 过滤；可展开收起，标题显示「共 N 条」
props.bind主表上的关联字段名（如 no），必须是主表数据里存在的字段
props.bindTo子表上的关联字段名（如 taskNo）。两表字段不同名时必须显式写，否则默认 bindTo = bind，一条都匹配不到
跳页用主表 columns[].actions 里的按钮（n-table__act_*_detail）—— 点按钮不会误触发选行
列表页三件套主表可配 query（查询条）/ toolbar（操作条）/ pagination（分页脚）

运行期自检（容器会替你兜底）

主表选中行的 bind 值在子表 bindTo 字段里一条都匹配不到、而子表本身有数据时， 容器会输出一条告警： 

主子表 n-md-task：主表 `no` 的值（ONSETE-20261016-0043）在子表字段 `taskNo`
中匹配不到任何行，请检查 bind / bindTo 是否写对

这类「bind/bindTo 写错导致子表永远为空」的错误肉眼极难发现，所以做成了运行期告警，并在校验器里对应一条反例。

契约详见 04-container-schema.md §6.7，可运行示例见 assets/examples/example-04-master-detail.json，页面骨架见 05-component-states.md §6.4。

2.5 跳转与页面关系

这是 P5 直截了当在页面维度的应用：原型不能是一堆孤岛，但也不该为了「完整」到处加跳转。 列表 → 详情的跳转成本很低，而「跳转写全 = 关系图自动成立」 —— 跳转本身就是页面关系的声明。

合成节点 id（容器内建）含义
<节点 id>__row_<i>表格第 i 行的行点击（需 props.rowClick: true）
<节点 id>__act_<i>_<key>表格第 i 行、操作列里 key 按钮的点击
<节点 id>__back页面返回（Header.props.back）
<节点 id>__ok / __cancelModal 的确认 / 取消（用 Modal 节点 id，不是 props.modalId；__cancel 内建关闭）
n-table__row_* / n-table__act_*_<key>通配目标：一条 interaction 覆盖所有行
  • navigate.params 里用 {{row.字段}} 按行带参（在源页求值），目标页用 {{变量名}} 渲染。
  • 目标页在 states[].vars 里留默认值，这样单独打开它也正常。
  • URL hash（#/page-id）即当前页，可分享、可浏览器前进后退；页面内「返回」不会跳出容器。
  • 所有 navigate 会自动抽成 pageGraph，渲染成顶部「关系图」。

2.6 画布交互（缩放 / 平移 / 标注）

这是 P1 自然在评审工具维度的应用：原型被左栏、右栏挤压是常态， 不要靠缩小浏览器窗口或删页面来腾空间 —— 中栏自带缩放与平移，且手势要跟手、可预期。

操作方式说明
缩放⌘/Ctrl + 滚轮（以光标为锚点）；⌘/Ctrl + 0/+/- 复位/放大/缩小；工具条 − 100% +范围 25%–300%
适应宽度工具条「适应宽度」把原型压回中栏可视宽（等价 100%），不产生横向滚动条
平移拖拽画布；空格拖拽；鼠标中键拖拽；「✋ 平移」常驻模式平移模式与标注模式互斥（开一个自动关另一个）
标注「✍ 标注」模式点原型任意位置加气泡；点气泡看/改/删气泡严格贴合锚定节点
标注指令顶部「⇪ 标注指令」把标注导出为可直接交给 AI 的修改指令，含锚定节点、节点类型、属性摘要、渲染条件
i

标注锚定用归一化坐标 + 画布盒基准，与缩放倍率无关：评审时可以先 ⌘+滚轮放大看细节、再「适应宽度」缩回纵览， 气泡始终贴在锚定节点上（回归测试跨 100%~152% 偏差 < 0.8%）。

2.8 行为先于界面（按钮可用性 · 页面切分）

这是 P2 确定与 P5 直截了当在行为维度的应用，也是本 skill 最容易做错的地方。 一个按钮该不该可点，不是画页面时的审美决定，而是业务事实：谁、在单据的哪个状态、能做什么。 把这件事留到画页面时「顺手决定」，结果必然是「审批中的单据照样摆着能点的提交按钮」。

两条硬规则

规则 1

可用性来自 capability，不写死

业务按钮的 props 里写 capability: "cap-xxx"，由「角色 × 当前状态」算出可用性； 三种不可用策略各有语义：
disabled（默认）—— 存在但当前不行，置灰 + 悬停说明原因；
hidden —— 这个角色不该知道有这功能，直接不渲染；
reject —— 允许点，点了才告知为什么不行（用于需要引导的场景）。

规则 2

一个页面只干一件事

页面的 contract 声明它拥有哪些命令（owns）、解决谁的什么决策（decision）、 提交边界在哪（submitBoundary）。
五条合并判据全中才合（同角色 / 同对象 / 同决策 / 同提交边界 / 同屏可读）； 命中任一拆分信号就拆（角色不同 / 生命周期阶段不同 / 提交边界不同 / 信息超两屏 / 完成条件不同 / 权限差异大 / 入口不同）。

策略原型表现什么时候用
disabled按钮置灰、保留指针事件，悬停出 title 说明原因 功能存在、用户也有权限，只是当前状态不允许。默认选它 —— 让用户知道「这条路存在，只是现在走不了」。
hidden不渲染（DOM 里没有） 用户不该知道这个能力存在（无权限、或该角色根本不该看到）。慎用：隐藏过多会让用户以为系统没这功能。
reject虚线边框 + 警告色，可点击，点击后 toast 说明 需要引导而非阻断：让用户点一下才知道「要先去完成前置步骤」。
i

怎么验：容器顶栏的「单据状态」下拉可以切换当前单据状态，按钮会实时按策略变灰 / 消失； PRD 面板右栏会把 capabilities 渲染成一张命令策略矩阵（行＝命令，列＝状态）， 点列头即可切换状态对照。走查时把状态挨个点一遍，比读一百行文字快。

3PRD 内容结构

PRD 的结构必须与原型、标注、状态机一一对应 —— 这是「研发拿去能直接转技术文档」的前提。 整份产物按五层组织，最终交付的文档按 12 章组装。顺序不能反：行为层没定，原型层就是在猜。

五层结构

① 文档层
PRD 板块 boardPlan → 页面 page.prd
目标 / 交互说明 / 业务规则 / 页面状态 / 验收
② 行为层
任务 tasks + 命令策略 capabilities + 页面职责 page.contract
谁（actor）在什么状态（from）下能对什么对象（entity）做什么（动作），不可用时是隐藏、置灰还是点了才拒（policy）；
页面承诺拥有哪些命令（owns）、解决谁的什么决策（decision）、提交边界在哪（submitBoundary）
③ 原型层
组件树 componentTree + 交互 interactions + 页面状态 states
递归 Node、事件 → 动作序列、状态变量与覆写
④ 标注层
page.annotations
锚定节点（推荐）+ 归一化坐标兜底、分类、状态流转、处理记录
⑤ 状态机层
requirements[] + stateMachines[]
EARS 条目（角色/触发/规则/状态机/预期/验收）+ 实体生命周期

对应铁律（校验器会检查）

  1. page.prd.sections 里的每条「交互说明」，在 page.interactions 里必须有对应交互。
  2. page.prd.reqIds 必须能在 requirements 里找到，且这些需求的 pageId 指向本页。
  3. page.states 的每个状态，在 PRD 的「页面状态」小节里必须有说明。
  4. 状态机里的每个状态，在原型里必须可见（Tag / Badge / 状态条）。
  5. 业务按钮必须指向 capability，不写死 disabled —— 可用性由「角色 × 单据状态」算出来。
  6. 一条命令只能有一个主页面（contract.owns 不得被两页同时声明），否则用户不知道该去哪操作。
  7. 状态机的每条人工转移必须有按钮入口（system: true 的自动流转除外），否则状态永远走不到。

EARS 与质量门禁

需求条目走 EARS 句式（五种：Ubiquitous / Event-driven / State-driven / Unwanted / Optional），字段固定 6 个：

字段含义
role谁（角色）
trigger什么条件下（触发）
rule系统必须做什么（规则，单一响应）
stateMachine涉及哪个状态机 / 状态
expected预期结果（可观测）
acceptance验收条件（可勾选、可测试）
门禁

无主观词（「友好」「快速」「尽量」）、无实现细节（技术栈 / 表结构）、单一响应（一条需求一件事）、可验收（能写成测试用例）。四条不过则重写。

另外三条硬约定：推断必标（AI 推断的内容 source: "inferred" 并写进 openQuestions）； 数据模型不能只在正文里（实体/字段/主外键进顶层 dataModel，派生指标进 derived[] 且必须有 fallback）； 每页要有流程图（prd.sections 里至少一个 type:"flow" 小节，有 start/end、判定出边带 label、无孤岛节点）。
