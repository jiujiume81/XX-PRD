# 需求澄清（Requirement Clarification）

> 澄清是整套流程的**第一道闸门**。没有澄清就写 PRD，等于把不确定性埋进交付物里。
> 目标：把用户口头的、零散的想法，收敛成 4 份可确认的 shaping 文档 + 1 份待澄清问题清单。

---

## 1. 澄清问题清单（Clarification Checklist）

按 8 个维度提问，**每轮最多抛 5~7 个问题**，避免一次性压垮用户。能用选项就不要用开放题。

### 维度 A：产品定位（Why / Who）
- 这个产品/功能解决谁的什么问题？没有它会怎样？
- 一句话说清价值主张（"让 ___ 在 ___ 内完成 ___"）。
- 目标用户是谁？他们的核心诉求与痛点？
- 明确的**非目标**是什么？（这次不做什么）
- 成功怎么衡量？北极星指标 / 关键结果。

### 维度 B：范围与边界（Scope）
- 本期必做的 P0 有哪些？可以延后的 P1/P2？
- 是否依赖已有系统 / 外部服务？
- 有无合规、权限、数据敏感度约束？

### 维度 C：用户与角色（Who）
- 有哪几类角色？各自的权限差异？
- 主角色是谁？次要角色如何被影响？
- 是否需要多租户 / 组织隔离？

### 维度 D：用户流与场景（Flow）
- 用户从哪进入？典型任务路径是什么？
- 高频路径 vs 低频路径分别是什么？
- 有哪些异常/边界场景？（超时、并发、断网、空数据、超限）

### 维度 E：功能与规则（What / Rule）
- 每个模块的核心动作有哪些？
- 关键业务规则？校验规则？额度/频率限制？
- 计算逻辑、排序规则、默认值？

### 维度 F：状态与生命周期（State）
- 核心实体有哪些状态？状态如何流转？谁能触发？
- 是否存在不可逆状态？如何回退/撤销？
- 终态是什么？

### 维度 G：数据与集成（Data）
- 数据从哪来？如何存？保留多久？
- 需要哪些第三方集成 / 通知渠道？
- 是否需要导入导出？

### 维度 H：体验与交付（UX）
- 目标端：Web / 移动 / 小程序 / 桌面？
- 有无品牌/设计规范约束？
- 性能、可访问性、多语言要求？
- 交付节点与验收方是谁？

## 2. 澄清话术模板

**开场（不要问"你要什么"，要给脚手架）：**

> 我先把这件事拆成 5 个问题，你按顺序答就行，答不上来的写"待定"我来补默认值：
> 1. 这个功能解决谁的什么问题？
> 2. 用户从哪进来、要完成什么动作？
> 3. 涉及哪几类角色，权限有差异吗？
> 4. 有哪些明确的"不做"？
> 5. 怎么算做成了？

**收敛（每轮结束必做）：**
> 我按你刚才的回答整理了 4 份文档（产品定位 / 用户流 / 模块清单 / 页面清单），
> 另外有 3 个点我拿不准，列在"待澄清问题"里 —— 你确认下，或者直接说"按你的默认值来"。

**冲突处理：** 当用户回答自相矛盾时，不要自行选择，把两个版本并列回抛：
> A 说"要支持 100 人团队"，B 说"先做 10 人以内"。这会影响列表性能方案，你选哪个？

## 3. 文档模板

### 3.1 产品定位文档（Product Positioning）

```markdown
# 产品定位：{产品名}

## 一句话定位
让 {目标用户} 在 {场景/时间} 内完成 {核心动作}。

## 定位陈述
- 面向：{目标用户}
- 他们的问题是：{痛点}
- 本产品是：{品类}
- 能提供：{核心价值}
- 不同于：{替代方案}
- 因为：{差异化}

## 目标用户
| 角色 | 描述 | 核心诉求 | 痛点 |
|---|---|---|---|

## 核心价值
{1-3 条}

## 非目标（Non-Goals）
- 不做：…
- 不做：…

## 成功指标
| 指标 | 类型 | 目标值 | 观测方式 |
|---|---|---|---|
|  | leading/lagging |  |  |
```

### 3.2 用户流文档（User Flow）

```markdown
# 用户流：{产品名}

## 流 1：{流名称}
- 角色：{角色}
- 目标：{用户要达成什么}
- 前置条件：…
- 主路径：
  1. {步骤} → 页面 {P1}
  2. {步骤} → 页面 {P2}
  3. …
- 分支/异常：
  - 若 {条件} 则 {分支路径}
- 后置结果：…
- 对应需求：REQ-xxx

## 全局流关系
{用 Mermaid 或文字描述页面之间的跳转关系}
```

```markdown

## 范围边界
- 本期包含：…

```

### 3.4 页面清单文档（Page Inventory）

```markdown

| 页面 | 所属模块 | 路由 | 页面目标 | 入口 | 出口 | 关键状态 |

## 页面状态覆盖检查
| 页面 | 默认态 | 加载态 | 空态 | 异常态 | 无权限态 |
|---|---|---|---|---|---|
| 任务列表页 | ✅ | ✅ | ✅ | ✅ | ⬜（不适用，原因：…）|
```

## 4. 澄清完成判据（Definition of Ready）

全部满足才可进入需求分析（EARS）阶段：

- [ ] 产品定位文档已产出且用户确认
- [ ] 至少 1 条主用户流已闭环（有明确入口和出口）
- [ ] 模块清单已定，优先级明确
- [ ] 页面清单已定，每页四态覆盖情况已标注
- [ ] 待澄清问题清单中 **P0 问题已全部有答案或已给默认值**
- [ ] 非目标已明确写出（≥1 条）

> 未满足时，**不要进入下一步**，把缺口显式告知用户并给出默认方案征求意见。

## 5. 待澄清问题清单（Open Questions）

用统一结构管理，写进 JSON 的 `openQuestions`：

```jsonc
{ "id": "q-1", "question": "是否需要支持子任务？", "owner": "PM", "status": "open", "answer": "" }
```

规则：
- 每个问题必须能**落到某个字段/规则/页面**，否则是伪问题，删掉。
- 问题解决后填 `answer` 并把 `status` 改为 `resolved`，**不要删除**（保留决策痕迹）。
- AI 自己推断出的假设，也要写成一条 question，`owner` 填 `AI`，`answer` 写默认值并标记 `status: "assumed"`。
