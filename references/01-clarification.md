# 需求澄清（Requirement Clarification）

> 澄清是整套流程的**第一道闸门**。没有澄清就写 PRD，等于把不确定性埋进交付物里。
> 目标：把用户口头的、零散的想法，收敛成 4 份可确认的 shaping 文档 + 1 份待澄清问题清单。

---

## 1. 澄清问题清单（Clarification Checklist）

按 9 个维度提问，**每轮最多抛 5~7 个问题**，避免一次性压垮用户。能用选项就不要用开放题。

### 维度 A：产品定位（Why / Who）
- 这个产品/功能解决谁的什么问题？没有它会怎样？
- 一句话说清价值主张（"让 ___ 在 ___ 内完成 ___"）。
- 目标用户是谁？他们的核心诉求与痛点？
- 明确的**非目标**是什么？（这次不做什么）—— **每条必须带四选一的理由码**：
  `not-enough-impact`（影响不够大）/ `too-complex`（代价过高）/ `separate-initiative`（另立专项）/ `premature`（时机未到）。
  **不带理由码的非目标视为没写。** 理由：非目标的作用不只是"划边界"，它还是**漏项的显影液** ——
  真正被漏掉的功能，往往会在"要不要做"的讨论里露一次面；不给理由码，这一面就白露了。
  反例（不合格）：`不做导出`。正例：`不做导出（premature：客户还没提出过批量取数需求，先不做）`。
- 成功怎么衡量？北极星指标 / 关键结果。

### 维度 B：范围与边界（Scope）
- 本期必做的 P0 有哪些？可以延后的 P1/P2？
- 是否依赖已有系统 / 外部服务？
- 有无合规、权限、数据敏感度约束？

### 维度 C：用户与角色（Who）
- 有哪几类角色？各自的权限差异？
- 主角色是谁？次要角色如何被影响？
- 是否需要多租户 / 组织隔离？

### 维度 D：用户流与场景（Flow）
- 用户从哪进入？典型任务路径是什么？
- 高频路径 vs 低频路径分别是什么？
- 有哪些异常/边界场景？（超时、并发、断网、空数据、超限）

### 维度 E：功能与规则（What / Rule）
- 每个模块的核心动作有哪些？
- 关键业务规则？校验规则？额度/频率限制？
- 计算逻辑、排序规则、默认值？

### 维度 F：状态与生命周期（State）
- 核心实体有哪些状态？状态如何流转？谁能触发？
- 是否存在不可逆状态？如何回退/撤销？
- 终态是什么？
- **每个状态下，哪些角色能执行哪些动作？不能执行时按钮应该隐藏、置灰，还是点了才拒绝？**
- **系统自动流转有哪些？**（定时任务、支付回调、超时关闭 —— 这些不需要按钮，要单独标出来）
- 有没有并发场景？（两个审批人同时处理同一张单，后提交的人看到什么）

### 维度 F2：任务与页面归属（Task / Page）
- 每类角色各自要**完成的一件事**是什么？判断依据是什么？什么算做完？
- 这些事里，哪些必须分开做（不同角色 / 不同提交时机 / 隔几天再做）？
- 哪些信息必须**同屏对照**才能做判断？（凭证 + 金额 + 历史）
- 一个页面里，点「保存」保存的是什么？有没有一块保存了另一块还没填的情况？

### 维度 F3：一对多与角色闭环（**必问位，不许跳过**）

这两个问题对应 `13-requirements-accuracy.md` 的 R2 / R3，漏问的代价是"整个结构性功能缺失"，
而不是"细节不准"。所以它们是**固定问题**，每个需求都要问一遍：

- **一对多**：一条主记录下会不会挂**多条**同类东西（多条任务 / 多条措施 / 多条明细）？
  如果是 —— 这些子项**有自己的状态**吗（不是主单据状态的影子）？**有自己的负责人**吗？
  三问全中 → 必须建主子结构，且子表不能靠"阶段列"区分两类单据。
  原文里出现 `分发至 / 各负责人 / 多个 / 分别 / 每个 / 明细 / 两种` 中任一词，本问必答。
- **角色闭环**：**每个角色**从哪进去干自己的活？把角色列一遍，逐个问「他打开系统，第一眼看到哪一页」。
  答"从别人的详情页点进去"= 没有待办入口，功能缺失。
  - **执行**与**验证**是不是**两个不同的人**？（同一个人的话，谁复核他？）
  - 执行人提交时要带什么佐证？验收人出结论时要答哪些项？

### 维度 G：数据与集成（Data）
- 数据从哪来？如何存？保留多久？
- 需要哪些第三方集成 / 通知渠道？
- 是否需要导入导出？

### 维度 H：体验与交付（UX）
- 目标端：Web / 移动 / 小程序 / 桌面？
- 有无品牌/设计规范约束？
- 性能、可访问性、多语言要求？
- 交付节点与验收方是谁？

## 2. 澄清话术模板

**开场（不要问"你要什么"，要给脚手架）：**

> 我先把这件事拆成 5 个问题，你按顺序答就行，答不上来的写"待定"我来补默认值：
> 1. 这个功能解决谁的什么问题？
> 2. 用户从哪进来、要完成什么动作？
> 3. 涉及哪几类角色，权限有差异吗？
> 4. 有哪些明确的"不做"？
> 5. 怎么算做成了？

**收敛（每轮结束必做）：**
> 我按你刚才的回答整理了 4 份文档（产品定位 / 用户流 / 模块清单 / 页面清单），
> 另外有 3 个点我拿不准，列在"待澄清问题"里 —— 你确认下，或者直接说"按你的默认值来"。

**冲突处理：** 当用户回答自相矛盾时，不要自行选择，把两个版本并列回抛：
> A 说"要支持 100 人团队"，B 说"先做 10 人以内"。这会影响列表性能方案，你选哪个？

## 4. 澄清完成判据（Definition of Ready）

全部满足才可进入需求分析（EARS）阶段：

- [ ] 产品定位文档已产出且用户确认
- [ ] 至少 1 条主用户流已闭环（有明确入口和出口）
- [ ] 模块清单已定，优先级明确
- [ ] 页面清单已定，每页四态覆盖情况已标注
- [ ] 待澄清问题清单中 **P0 问题已全部有答案或已给默认值**
- [ ] 非目标已明确写出（≥1 条），**且每条带四选一的理由码**（`not-enough-impact` / `too-complex` / `separate-initiative` / `premature`）
- [ ] **维度 F3 已答**：一对多（是否多实例 / 子项有无独立状态 / 有无独立负责人）与角色闭环（每个角色从哪进去干活）都有明确答案

> 未满足时，**不要进入下一步**，把缺口显式告知用户并给出默认方案征求意见。

## 5. 待澄清问题清单（Open Questions）

用统一结构管理，写进 JSON 的 `openQuestions`：

```jsonc
{ "id": "q-1", "question": "是否需要支持子任务？", "owner": "PM", "status": "open", "answer": "" }
```

规则：
- 每个问题必须能**落到某个字段/规则/页面**，否则是伪问题，删掉。
- 问题解决后填 `answer` 并把 `status` 改为 `resolved`，**不要删除**（保留决策痕迹）。
- AI 自己推断出的假设，也要写成一条 question，`owner` 填 `AI`，`answer` 写默认值并标记 `status: "assumed"`。
