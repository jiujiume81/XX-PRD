# 09 · 行为建模：角色 × 状态 × 命令

> 这份文档解决一类**看起来完全正常、用起来处处别扭**的原型：
> 单据有五个状态，页面上五个按钮却永远可点；审批通过后「编辑」还在；已作废的单子还能「提交」。
>
> 根因不是「漏画了几个禁用态」，而是**信息被拆开记录、没有连成语义链**：
> 角色写在 `users[]`、状态写在 `stateMachines[]`、按钮画在 `componentTree` 里，
> 三者之间没有任何强制对应关系。于是状态机可以写得很好，按钮也可以画得很全，两者却互不相干。

---

## 0. 一句话原则

> **先有「谁能对什么状态做什么」，才有按钮。**
> 按钮是命令的**表现**，不是页面的装饰。

判断自己有没有做到，只需回答一个问题：

> 随便指一个按钮，能不能立刻说出**它在哪些状态下可点、在哪些状态下不可点、不可点时用户看到什么**？

答不上来，就说明这个按钮是「照着后台长相补出来的」，不是从业务规则推导出来的。

---

## 1. 行为链

原型里的每一个可点元素，都应该能沿着这条链回溯：

```
角色 actor
  → 用户目标 goal
    → 业务任务 task
      → 命令 command
        → 允许状态 from[]
        → 前置条件 guard
          → 状态转移 to
            → 页面位置 page
              → 组件节点 node
                → 验收条件 acceptance
```

链上任何一环缺失，都会在某个场景下暴露：

| 断点 | 典型症状 |
|---|---|
| 有命令、无允许状态 | 任何状态都能点，审核完还能改 |
| 有状态、无不可用策略 | 按钮直接消失（用户不知道为什么），或点了没反应 |
| 有策略、无拒绝原因 | 置灰了，但没人知道为什么灰 |
| 有命令、无页面归属 | 同一个动作在三个页面重复出现，各写各的 |
| 有命令、无验收 | 只测了成功路径，权限不足 / 状态不符没人验 |

## 2. 三个建模动作

### 2.1 业务任务清单（Task）

在画页面之前，先把「用户要完成的事」列出来。**任务不是功能**：

| | 功能（Feature） | 任务（Task） |
|---|---|---|
| 描述 | 「审批功能」 | 「主管在 5 分钟内判断这张单该不该放款」 |
| 有完成态 | 通常没有 | 有（做出了结论） |
| 有角色 | 常常含糊 | 明确 |
| 决定页面 | 不能 | 能 |

每条任务写四件事：**谁 / 想达成什么 / 判断依据是什么 / 什么算完成**。

```json
{
  "id": "task-review",
  "name": "完成退款审批",
  "actor": "u-agent",
  "goal": "在看完凭证与历史记录后给出通过或驳回结论",
  "inputs": ["退款金额", "凭证图片", "用户历史退款次数"],
  "doneWhen": "单据离开「待初审」状态并留下审批人",
  "pages": ["page-refund-review"]
}
```

任务清单是页面切分的**唯一依据**（见 `10-page-decomposition.md`）。

### 2.2 命令策略表（Capability）

每条命令一行，回答七个问题。**这是本轮最重要的产出物**：

| 字段 | 必填 | 回答什么 |
|---|---|---|
| `id` | ✓ | 稳定标识，组件用 `props.capability` 引用 |
| `name` | ✓ | 用户看到的动作名（「通过并转财务」） |
| `entity` | ✓ | 作用于哪个业务实体 |
| `actor` | ✓ | 哪些角色可以执行（引用 `users[].id`） |
| `from` | ✓ | 允许执行的业务状态 id 列表（空数组 = 不限状态） |
| `guard` | | 状态之外的前置条件（金额、库存、字段完整度） |
| `policy` | ✓ | 不满足时怎么办：`hidden` / `disabled` / `reject` |
| `reason` | ✓（policy≠reject 时） | 为什么不能执行，写给用户看 |
| `to` | | 执行成功后进入的状态 |
| `effect` | | 副作用（写审批人、发通知、扣库存） |
| `page` | | 主要出现位置 |
| `requirement` | | 对应哪条 EARS 需求 |
| `onFail` | | 失败时用户能做什么（重试 / 改数据 / 找谁） |

#### policy 怎么选（三选一，不要混用）

| policy | 什么时候用 | 组件表现 | 用户感受 |
|---|---|---|---|
| `hidden` | 该角色**根本不该知道**有这个动作；或状态与动作语义矛盾（草稿态的「撤回」） | 不渲染 | 世界干净，但要知道自己在哪 |
| `disabled` | 动作**存在且未来可做**，只是当前状态/权限不满足 | 置灰 + 悬浮说明原因 | 「我知道能做，但现在不行」 |
| `reject` | 需要**先让用户尝试**才知道不满足（复杂校验、并发冲突、需要解释的业务规则） | 正常外观，点击后提示原因 | 「我试了，它告诉我为什么」 |

**默认选 `disabled`。** 只有满足以下之一才用另外两个：

- 用 `hidden`：暴露这个动作会**误导**用户（让他以为流程可以倒回去），或属于**越权信息**。
- 用 `reject`：拒绝原因**依赖运行时数据**（库存被抢、单据被别人改过），画面上无法预先判定。

> 常见错误：所有不可用动作都 `hidden`。结果是同一页面在不同状态下按钮忽隐忽现，
> 用户每次都要重新找按钮在哪 —— 这比置灰更让人不安。

#### `reason` 的写法

必须是**用户能据此行动**的句子，不是错误码：

| 差 | 好 |
|---|---|
| 状态不允许 | 仅「待初审」的单据可以审批，当前为「已放款」 |
| 无权限 | 审批需要「财务主管」角色，你是「客服」 |
| 校验失败 | 还有 2 个必填项未填：收款账户、开户行 |
| 库存不足 | 可售库存 3 件，本单需要 10 件 |

### 2.3 状态机补全

命令策略表会反向暴露状态机的漏洞。补两类东西：

1. **`guard`**：转移的守卫条件必须写具体（「所有巡检项不为待巡检」而不是「条件满足」）。
2. **系统自动转移**：由定时任务 / 外部回调触发的转移（超时自动关闭、支付回调），
   标 `"system": true`，**不需要**对应按钮。校验器据此区分「漏了入口」和「本来就没人点」。

```json
{ "id": "t-auto-close", "from": "pending_pay", "to": "closed",
  "trigger": "超过 7 天未放款", "system": true, "guard": "无人工操作", "action": "释放冻结金额" }
```

### 2.4 `ui` 三态：行为必须落到界面

状态机只证明「流程想清楚了」，证明不了「页面能点出来」。`ui` 是这条链上唯一机器可检的连线，
`transitions[]` 与 `requirements[]` 两处都要写，**写法同构、含义同构**：

| 写法 | 含义 | 用在哪 |
|---|---|---|
| `{"interactionId": "ix-xxx"}` | 由某个交互触发（按钮 / 行内动作 / 弹窗确认） | 两处都可用 |
| `{"kind": "system"}` | 系统自动（定时任务 / 外部回调 / 自动建单） | 两处都可用 |
| `{"kind": "page-enter"}` | 进页面即满足，不需要点击 | **仅 `requirement.ui`** |

**两处唯一必须记住的差异：一条转移可能被多个页面触发，所以 `transitions[].ui` 自带 `pageId`；
`requirement.ui` 不重复写 `pageId`，它用同级 `requirement.pageId` 定位。**

**需求侧不许写 `pageId`，写了是 L3 硬错（两档都 ERROR）。** 页面归属只有一个真源，就是需求同级的
`pageId`；`ui` 里再写一份，等于同一个事实有两个来源 —— 改了一处另一处不动，谁也说不清哪个算数。
校验器对此直接报错（`scripts/validate_prd_json.py:819`），而不是"忽略多余字段"：
**多余字段被静默忽略，比报错更危险** —— 写的人以为生效了，读的人以为那是真源。

> `{"kind":"page-enter"}` 写到转移上是**错**，不是"暂未实现"：校验器只对 `kind == "system"` 放行，
> 其余一律按人工转移处理，于是它会要求 `pageId` 并报「缺少 pageId」（默认档 WARN / 交付档 ERROR）。
> 别指望它被识别成第三种态。

**什么算系统行为：三个入口等价，只许一处实现。** 任一成立即算，不要求写 `ui`：

- `"system": true`（老写法，`tests/check_generators.py` 的 `count_system()` 数的就是它）
- `"role": "system"`
- `"ui": {"kind": "system"}`（本节的新写法）

判定只在 `scripts/validate_prd_json.py` 的两处实现：`ui_kind_is_system()` 与 `transition_is_system()`。
不要在生成器、检查器里各写一遍 —— 一旦各长一套，「什么算系统行为」会在两个检查里给出不同答案，
而且是"两边都 PASS、只是口径不同"的静默分叉，比报错难查得多。

**分层与档位：什么 WARN、什么必须 ERROR。**

| 层 | 情况 | 默认档 | `--profile=delivery` |
|---|---|---|---|
| **L1** | `ui` 缺失 / 转移缺 `pageId` / 转移缺 `interactionId` / 转移的 `ui` 不是对象 | WARN | **ERROR** |
| **L2** | 悬空引用：`pageId` 不存在、`interactionId` 不在该页 `interactions` 中、需求有 `interactionId` 却没有 `pageId` | **ERROR** | **ERROR** |
| **L3** | 结构错：需求的 `ui` 不是对象 / `kind` 不是 `system` 或 `page-enter` / 既无 `interactionId` 也无合法 `kind` / 需求的 `ui` 里出现 `pageId` | **ERROR** | **ERROR** |

分层的唯一理由是**存量产物**：L1 是"还没写"，一刀切 ERROR 会让升级当天所有老 PRD 全红，
人的第一反应是关掉检查而不是补页面；L2 / L3 是"写错了"，写错没有过渡期。
档位表见 `04-container-schema.md` §13.1。

**为什么不用 `pattern` 当前提。** `pattern`（`event-driven` / `state-driven` / …）看起来是现成的入口判据，
实测不可信：`REQ-ITK-007` 是人工点「审核驳回」，标成了 `state-driven`；`REQ-NTC-007`（回传 WMS）、
`REQ-SMP-001`（自动生成取样任务单）是系统动作，标成了 `event-driven`。拿它当"这条需求该有按钮"的前提，
真缺陷会**静默漏检** —— 判据自己先错了，后面越严越糟。

**同一 trigger 何时合法、何时是歧义。** `example-05` 的 `t-po-6`（draft→cancelled）与
`t-po-7`（pending→cancelled）共用 trigger「采购员点击「取消」」和同一个 `interactionId`，
看着像重复，其实是**一个按钮、两种来源状态、同一终态**：

- `from` 不同、`to` 相同 → **靠 `from` 消歧，属正确建模**，不要合并成一条；
- 真歧义的判据是「**同一 `from`** + 同一 trigger + **不同 `to`**」—— 那才是同一个按钮会走到两个终态，
  用户点下去系统自己也不知道该去哪。

## 3. 从策略表推导按钮

不要先摆按钮再想行为，按这张表反查：

| 命令的 `from` 覆盖 | 页面上的表现 |
|---|---|
| 覆盖该实体全部状态 | 普通按钮，无需 `capability`（如「查看」「复制单号」） |
| 覆盖部分状态 | 必须写 `capability`，由容器按当前状态求值 |
| 只覆盖 1 个状态且是终态 | 通常 `hidden`（终态不该出现可逆动作） |
| 有 `guard` 但无状态限制 | `capability.from` 留空，`guard` 写进 `reason` 或由 `reject` 承接 |

**同一命令在多个页面出现时，必须引用同一个 `capability.id`。** 这是防止「列表页能删、详情页不能删」这类不一致的唯一手段。

## 4. 两种取值方式：行级 vs 页面级

同一个 `capability` 在两种页面里的状态来源不同，容器已内建处理：

| 场景 | 状态来源 | 写法 |
|---|---|---|
| **列表 / 表格行内动作** | 该行记录的 `status` 字段（中文名或状态 id 都认） | `columns[].actions[].capability` |
| **详情 / 表单页主按钮** | 页面声明的 `page.entity` 对应的**模拟状态**（顶部「单据状态」下拉） | `props.capability` |

字段名不是 `status` 时，用 `stateField` 指定：

```json
{ "id": "cap-ship", "stateField": "orderStatus", "from": ["paid"], "policy": "disabled" }
```

> 详情页之所以用「模拟状态」而不是真实数据：原型是给人看的，
> 评审时需要**当场切换状态**验证按钮行为，而不是改 JSON 重新生成。

## 5. 失败与恢复

只写成功路径的命令，等于只写了一半。每条命令至少想清楚三件事：

| | 要回答 | 落到哪里 |
|---|---|---|
| 失败原因 | 可能因为什么失败（校验 / 权限 / 并发 / 下游超时） | `onFail` |
| 用户看到什么 | 错误文案、错误位置（字段级 / 表单级 / 全局） | 页面 `states` 的 error 态 + `reason` |
| 下一步做什么 | 重试 / 修改数据 / 联系谁 / 等待 | `onFail` 的行动建议 |

**并发冲突是最常被漏的一类**：两个人同时审批同一张单。原型里至少要有一个「单据已被他人处理」的提示态，
否则开发实现时只能自己拍脑袋。

## 6. 权限的三个粒度

「谁能做什么」不止一种，混在一起写就会漏：

| 粒度 | 含义 | 例子 | 落在哪 |
|---|---|---|---|
| **功能权限** | 这个角色有没有这个动作 | 客服不能放款 | `capability.actor` |
| **数据范围** | 能操作哪些记录 | 客服只能看自己名下的单 | `capability.dataScope` + 列表默认筛选 |
| **字段级** | 同一表单里哪些字段可编辑 | 财务能改金额，客服只能看 | 字段 `disabled` + `disabledReason` |

三者都要在原型上**可见**：

- 功能权限 → 按钮置灰/隐藏 + 原因
- 数据范围 → 列表页的默认查询条件、空态文案（「你名下暂无待处理单据」）
- 字段级 → 输入框置灰 + 悬浮说明

> 只做功能权限是最常见的半成品：按钮灰了，但用户点进详情仍能改金额。

## 7. JSON 写法

### 7.1 根级 `capabilities[]`

```json
"capabilities": [
  {
    "id": "cap-refund-approve",
    "name": "通过并转财务",
    "entity": "RefundOrder",
    "actor": ["u-agent"],
    "from": ["reviewing"],
    "guard": "申请信息完整且凭证已上传",
    "policy": "disabled",
    "reason": "仅「待初审」的单据可以审批，当前为「已放款」",
    "to": "pending_pay",
    "effect": "记录初审人与时间，通知财务",
    "page": "page-refund-review",
    "requirement": "r-3",
    "onFail": "凭证缺失时提示补充上传，停留在当前页"
  },
  {
    "id": "cap-refund-edit",
    "name": "修改申请",
    "entity": "RefundOrder",
    "actor": ["u-customer"],
    "from": ["draft", "rejected"],
    "policy": "hidden",
    "reason": "已提交的单据不可修改，如需变更请撤回后重提",
    "page": "page-refund-apply"
  }
]
```

### 7.2 页面绑定实体

```json
{ "id": "page-refund-review", "entity": "RefundOrder", "stateMachine": "sm-refund", "...": "..." }
```

`entity` 让容器知道去哪个状态机取状态；`stateMachine` 可省略（按 entity 自动匹配）。

### 7.3 按钮引用

```json
{ "id": "n-btn-approve", "type": "Button",
  "props": { "text": "通过并转财务", "type": "primary", "capability": "cap-refund-approve" } }
```

### 7.4 表格行内动作引用

```json
{ "dataIndex": "op", "type": "action",
  "actions": [
    { "key": "detail", "label": "详情" },
    { "key": "edit", "label": "修改", "capability": "cap-refund-edit" },
    { "key": "del", "label": "作废", "type": "danger", "capability": "cap-refund-void" }
  ] }
```

### 7.5 容器怎么呈现

| policy | 渲染结果 | 点击行为 |
|---|---|---|
| `hidden` | `display:none` | 不可点 |
| `disabled` | 灰底灰字 + `cursor:not-allowed` + `title=reason` | **可点**，弹出 reason 提示（不是静默无反应） |
| `reject` | 正常外观，虚线边框 + 警告色 | 正常执行交互；若无交互则兜底提示 reason |

> 置灰按钮**保留指针事件**是刻意设计：原型评审时，评审人会去点灰按钮问「为什么不能点」，
> 这时应该当场给出原因，而不是让页面毫无反应。

## 8. 自检清单

交付前逐条回答，答不上就是没做完：

1. 每个状态机转移，要么有对应 `capability` **且** `ui` 指向该页真实存在的 `interactionId`，要么是 system
   （`system: true` / `role: "system"` / `ui.kind: "system"` 三者任一）？**"有 capability"不等于"页面有按钮"**——
   capability 只说这条命令被允许，说不说得出按钮在哪个页面、点哪个东西，全靠 `ui`。
2. 每个写进原型的业务按钮，都指向一个 `capability`（除纯查看类）？
3. 每条 `capability` 的 `from` 都是真实存在的状态 id？
4. 每条 `capability` 的 `policy` 都选了，且 `reason` 是用户能行动的句子？
5. 终态（已完成 / 已作废 / 已关闭）下的可逆动作，是不是都 `hidden` 或 `disabled`？
6. 同一命令在列表页和详情页引用的 `capability.id` 是否一致？
7. 有没有至少一个 `reject` 或 error 态，覆盖「单据已被他人处理」这类并发冲突？
8. 字段级权限（只读字段）有没有标出来？
9. 数据范围（「只能看我名下的」）有没有体现在列表默认筛选或空态文案里？
10. 每条 `capability` 都挂到了至少一条 EARS 需求？
11. 每条需求至少有一条验收条件覆盖**非法动作被拒绝**，而不只是成功路径？
12. 把顶部「单据状态」逐个切一遍，页面上的按钮是否都符合预期？
13. **每条需求**的 `ui` 是否指明它落在哪个按钮 / 哪次进入（`interactionId` / `system` / `page-enter`）？
    需求侧的 `ui` 不写 `pageId`，靠同级 `pageId` 定位（见 §2.4）。

## 9. 反模式

| # | 反模式 | 为什么错 | 怎么改 |
|---|---|---|---|
| 1 | 用 `disabled: true` 写死按钮 | 换一个状态就错了，且没有任何解释 | 改 `capability` + `from` |
| 2 | 所有不可用都 `hidden` | 按钮忽隐忽现，用户找不到东西 | 默认 `disabled` |
| 3 | `reason` 写成「状态不允许」 | 用户不知道该干什么 | 写清当前状态 + 允许状态 |
| 4 | 只做功能权限，不做字段级 | 按钮灰了但表单还能改 | 字段加 `disabled` + 说明 |
| 5 | 状态机写了 8 个状态，页面只有 1 个 | 状态机是摆设 | 用顶部状态下拉逐个验证 |
| 6 | 列表页行内动作不受状态约束 | 已完成的单还能「撤回」 | `columns[].actions[].capability` |
| 7 | 同一命令两个页面各写一套禁用逻辑 | 迟早不一致 | 共用 `capability.id` |
| 8 | 只画成功路径 | 失败时用户面对空白 | 补 error 态 + `onFail` |
