# 10 · 页面职责与功能切分

> 这份文档解决另一类常见问题：**一个页面里塞了三个功能的表单和两个详情**。
> 列表、编辑、审批、日志、关联单据全在一屏，看起来「信息很全」，实际每个人都要在一堆无关内容里找自己要的东西。
>
> 根因同样不是「不会排版」，而是**没有定义页面的职责边界**。
> 现有的 `goal` 字段只写了一句人话（「让客服在一屏内看完判断依据」），
> 它回答不了「这个表单为什么和那个详情在同一个页面」。

---

## 0. 一句话原则

> **一个页面 = 一个角色，在同一业务对象上，完成一件可以独立判断完成的事。**

三个限定词缺一不可：

- **一个角色**：不同角色的任务不该共用一个页面（权限、信息密度、操作习惯都不同）。
- **同一业务对象**：订单和它关联的优惠券可以同页；订单和客户档案不该同页。
- **可以独立判断完成**：用户能明确说「这件事我做完了」，而不是「我顺手看了几眼」。

---

## 1. 页面职责契约（Page Contract）

每个页面除 `goal` 外，必须写清六个字段。它不是文档装饰，是**校验器的输入**：

```json
"contract": {
  "task": "task-review",
  "actor": ["u-agent"],
  "entity": "RefundOrder",
  "owns": ["cap-refund-approve", "cap-refund-reject"],
  "submitBoundary": "single",
  "entryFrom": ["page-refund-list"],
  "doneWhen": "单据离开「待初审」并记录审批人"
}
```

| 字段 | 回答什么 | 缺失后果 |
|---|---|---|
| `task` | 这个页面服务哪条业务任务 | 页面变成功能堆叠 |
| `actor` | 主要使用者是谁（可多个，但要同质） | 权限逻辑无处安放 |
| `entity` | 主体业务对象是哪个 | 主子表、状态机接不上 |
| `owns` | **这个页面负责发起哪些命令** | 同一命令在多个页面重复实现 |
| `submitBoundary` | `single`（一次提交）/ `staged`（分步）/ `none`（只读） | 表单该不该有「保存」说不清 |
| `doneWhen` | 用户什么时候算完成 | 页面没有终点，永远可以再改 |

> `owns` 是切分的核心：**一条命令只能有一个「主页面」**。
> 其他页面可以引用（跳转过去执行），但不能各自实现一套。

---

## 2. 合并判据：五条全中才合并

把两块内容放同一个页面，必须同时满足：

1. **同一角色** —— 看这两块的是同一个人，且不需要切换身份。
2. **同一业务对象** —— 主体是同一条记录（同一张单、同一台设备）。
3. **同一决策** —— 两块信息服务于**同一个判断**（看凭证是为了决定批不批）。
4. **同一提交边界** —— 要么一起提交，要么都不提交；不存在「这块保存了那块没保存」。
5. **同屏可读完** —— 在 1440×900 下一屏（或一次滚动）能看完，不需要反复跳。

**任何一条不满足，就应该认真考虑拆。**

### 反过来的例子

| 场景 | 判定 | 理由 |
|---|---|---|
| 审批页：单据详情 + 凭证图片 + 审批按钮 | **合并** | 五条全中：客服、同一单据、同一判断、一次提交、一屏可读 |
| 审批页 + 该用户的历史退款记录 | **合并（折叠）** | 同一判断依据，但信息量大 → 折叠面板，不占主视线 |
| 审批页 + 审批通过后的「放款登记表单」 | **拆** | 角色变了（财务）、提交边界不同、可以隔几天做 |
| 商品列表 + 商品编辑表单 | **拆（抽屉）** | 提交边界不同；列表要保留上下文 → 抽屉 |
| 订单详情 + 订单日志 + 关联工单 | **合并（分区/折叠）** | 同一对象，但日志和工单是「查阅」不是「决策」→ 折叠或 Tab，不抢主区 |
| 客户档案 + 该客户的订单列表 | **拆** | 对象不同（客户 vs 订单），任务不同 |

## 3. 拆分判据：命中任一即拆

| # | 信号 | 说明 | 拆成什么 |
|---|---|---|---|
| 1 | **角色不同且都需要完整操作** | 客服填单、财务放款 | 两个页面，靠状态机串起来 |
| 2 | **生命周期阶段不同** | 创建 / 编辑 / 审批 / 归档 | 创建页 + 详情页（内含编辑入口）+ 审批页 |
| 3 | **提交边界不同** | 一块保存了另一块还没填 | 拆页面，或至少拆成独立表单 + 独立提交 |
| 4 | **信息量超过两屏** | 需要反复滚动才能对照 | 主信息留主区，次要信息进 Tab / 折叠 / 独立页 |
| 5 | **完成条件不同** | 一个「提交即完成」，一个「等对方处理」 | 拆页面，用状态表达等待 |
| 6 | **权限差异大** | 一半内容 A 角色看不到 | 拆页面或做字段级权限（优先拆） |
| 7 | **入口不同** | 一个从列表进，一个从消息通知进 | 拆页面，各自有独立入口与返回路径 |
| 8 | **角色缺待办入口** | 某角色在 `capabilities[].actor` 里有命令，但没有任何页面以它为主体 —— 他只能从别人的详情页"借道"操作 | **新增一个页面**（不是把它塞进别人的页面）。判据见 `13-requirements-accuracy.md` R3 |

### 关于「详情页 + 编辑」

这是最容易做错的一处。三种做法，按场景选：

| 做法 | 适用 | 代价 |
|---|---|---|
| 详情页内联编辑（字段直接可改） | 字段少（≤5）、改动频繁、无审批 | 容易误改，需要「保存/取消」边界 |
| 详情页 + 抽屉编辑 | 中等复杂度（6~15 字段），需要保留上下文 | 抽屉里滚动，字段多时拥挤 |
| 详情页 + 独立编辑页 | 复杂表单、分步、需要草稿 | 上下文丢失，返回成本高 |

**不要**把「编辑表单」和「只读详情」上下堆在同一个页面里 —— 用户会分不清哪些能改。

## 4. 四类最常见的「揉」

### 4.1 多角色任务揉一页

症状：页面顶部是「客服填写」，中部是「主管审批」，底部是「财务放款」。
问题：三个角色各自要滚过另外两个人的区域；权限无法表达；状态机被压平成一个「页面」。
改法：`page-apply`（客服）→ `page-review`（主管）→ `page-pay`（财务），靠 `entity` 状态串联。

### 4.2 不同生命周期阶段揉一页

症状：同一个页面既是「新建」又是「编辑」还是「查看」，靠 `mode` 变量切换。
问题：三种模式的字段可编辑性、按钮、校验规则都不同，最后写成三层 if。
改法：新建独立页（或抽屉），编辑用抽屉，查看用详情页。**同一页面最多承载两种模式**（查看 + 内联编辑）。

### 4.3 主子 + 明细编辑揉一页

症状：主表下面直接跟一个可编辑的明细表格，再加一个「新增明细」的表单区。
问题：三个提交边界（主表、明细行、新增表单）混在一起，用户不知道点「保存」保存了什么。
改法：主表 + 只读子表（`MasterDetail`）；明细的新增/编辑走抽屉或子页面，独立提交。

### 4.4 看板/报表 + 操作揉一页

症状：数据看板上每个卡片都能直接改数据。
问题：看板的任务是「看趋势」，不是「改数据」；误触代价高。
改法：看板只读 + 点击下钻到列表（带筛选条件），操作在列表/详情里做。

## 5. 拆开之后：导航要接得上

拆页面不是画完就完了，必须同时定义：

| 要素 | 要求 |
|---|---|
| **入口** | 每个页面至少一个 `entryFrom`；没有入口的页面是死页面 |
| **返回** | 详情/编辑页 `Header.back: true`；返回要回到**来的地方**，不是固定回列表 |
| **面包屑** | 层级 ≥3 时必须有，让用户知道自己在哪 |
| **带参跳转** | 列表 → 详情传 id（`/order/:id`），不要跳到「详情页」再让用户自己找 |
| **完成后去哪** | 提交成功后回列表并**保留筛选条件**，或停在详情展示新状态 |
| **中断恢复** | 长表单要能存草稿；离开前提示未保存 |

> 判断标准：**从任意页面出发，能不能只靠界面（不靠地址栏）回到首页并找到任意其他页面。**

---

## 6. 不该拆的情况

避免走向另一个极端（每个功能一页，点五次才完成一件事）：

- **强关联的只读信息**：详情 + 关联记录（折叠即可）
- **同一决策的多块依据**：金额 + 凭证 + 历史（同页，用分区）
- **高频切换的轻量操作**：列表行内的「通过/驳回」（弹窗确认即可，不必跳页）
- **配置类页面**：表单虽长但同质（如系统参数），一页分组即可

## 7. JSON 写法

```json
{
  "id": "page-po-detail",
  "name": "采购订单详情",
  "route": "/purchase/order/:poNo",
  "parentId": "page-po-list",
  "entity": "PurchaseOrder",
  "stateMachine": "sm-po",
  "goal": "让采购员确认订单当前进度，并完成本角色可执行的动作",
  "contract": {
    "task": "task-po-track",
    "actor": ["u-buyer"],
    "entity": "PurchaseOrder",
    "owns": ["cap-po-submit", "cap-po-cancel"],
    "submitBoundary": "single",
    "entryFrom": ["page-po-list"],
    "doneWhen": "订单进入「待审批」或「已取消」"
  }
}
```

校验器会检查：

- `contract.task` 必须存在于 `tasks[]`（或至少有 `goal` 兜底）
- `contract.entity` 必须等于 `page.entity`
- `contract.owns[]` 里的 capability 必须存在，且 `capability.page` 指向本页
- 同一 capability 不能被两个页面的 `owns` 同时声明（ERROR）
- 页面若声明了 `entity` 且有状态机，但 `owns` 为空 → WARN（这个页面没有任何业务动作，是不是只读页？）

## 8. 自检清单

1. 每个页面能用一句话说清「谁在这里完成什么事」？
2. 每个页面有且只有一条 `task`？
3. 页面里的每个业务按钮，都能在 `contract.owns` 里找到？
4. 有没有两个页面 `owns` 同一条命令？
5. 有没有一个页面同时服务两个角色，且两边都要完整操作？
6. 页面里有没有「一半能改一半不能改」的表单？边界说清了吗？
7. 表单的提交边界是单一的吗？点「保存」保存的是什么？
8. 每个页面的 `entryFrom` 都不为空？
9. 详情页能返回「来的地方」而不是固定回列表？
10. 拆出去的页面，用户能不能不靠地址栏走回来？
11. 有没有为了「信息全」把只读内容塞进主视线？（应折叠或 Tab）
12. 有没有为了「职责单一」把一次任务拆成五次跳转？

## 9. 反模式

| # | 反模式 | 症状 | 改法 |
|---|---|---|---|
| 1 | 万能详情页 | 一个页面 6 个 Tab，每个 Tab 都是一套表单 | 按任务拆页，Tab 只放只读信息 |
| 2 | 角色混居 | 页面顶部「客服填写」中部「主管审批」 | 按角色拆，用状态机串 |
| 3 | 编辑与查看同屏堆叠 | 上半只读、下半可编辑，用户分不清 | 抽屉编辑 或 独立编辑页 |
| 4 | 主子表 + 明细编辑表单 | 保存按钮保存了什么说不清 | 子表只读，编辑走抽屉 |
| 5 | 无入口页面 | 做完了但没人能到达 | 补 `entryFrom` 与导航 |
| 6 | 每个动作一页 | 完成一件事点五次 | 轻量操作用弹窗确认 |
| 7 | 拆分后返回丢失上下文 | 从筛选结果进详情，返回变全量列表 | 返回保留筛选条件 |
