# 切片交付：把「一次性生成整个系统」拆成「一片一片做完」

> 需求一次给得越大，一次性产出的原型与 PRD 质量越差 —— 这不是模型"不努力"，
> 而是单轮要同时装下数据契约、全部页面、组件细节与业务规则，越往后越容易丢字段、
> 漏状态、把页面揉在一起。这篇讲怎么把交付拆成**可验收的最小闭环**。

---

## 1 为什么必须切片

一次性生成 20 个页面时，实际发生的事：

| 现象 | 机制 |
|---|---|
| 后面的页面字段越来越简 | 上下文里 schema 与前面页面挤占注意力，越靠后越依赖"顺手写法" |
| 状态机只覆盖前几个页面 | 业务规则与页面一起写，写到后半段已无余力回看 |
| 页面之间跳转接不上 | 跳转需要全局视野，一次性写完时很难回头改前面的 `entryFrom` |
| 校验器报一堆错，改一处牵动三处 | 没有中间验收点，错误在最后一次性暴露 |
| 想只改一个功能，却要重写整份 JSON | 没有交付单元，产物是"一坨"而不是"一叠" |

切片解决的正是这五件事：**每片都有独立的验收标准与校验点**，错了只回退一片。

---

## 2 切片单位：用户故事最小闭环

**一个切片 = 一个角色，为达成一个目标，走完一条主路径，并能独立验收。**

判定一个候选切片是否成立，四条全中才算：

1. **单角色**：主路径只有一个角色的操作（第二个角色出现就要拆，或标为"协作角色"）
2. **单目标**：能写成「让 ___ 完成 ___」，不是「管理 ___ 模块」
3. **主路径闭合**：从入口进得去、做得完、看得见结果，不需要等下一片才能"走通"
4. **可独立验收**：这片做完，业务方可以单独点开看并说"对/不对"

### 不要用「功能闭环」当切片单位

| 单位 | 例子 | 问题 |
|---|---|---|
| ❌ 功能闭环（模块级） | "订单管理" | 跨 4 个角色、6 个页面、20+ 命令，等于没切 |
| ❌ 页面级 | "订单列表页" | 只有界面没有行为，验收时走不通 |
| ⚠️ 技术分层 | "先做所有列表页，再做所有表单页" | 每片都不可独立验收，业务方看不出价值 |
| ✅ 用户故事最小闭环 | "采购员把请购单提交出去" | 一个角色、一次判断、一个结果 |

> 功能闭环可以作为**阶段目标**，但不能作为**交付单元**。切片的粗细应以"能不能单独验收"为准。

---

## 3 单片上限（超过就必须再切）

| 维度 | 上限 | 依据 |
|---|---|---|
| 页面数 | 4 | 再多人一次看不完，评审意见会互相干扰 |
| 命令（capability）数 | 6 | 命令超过 6 条，几乎必然跨角色或跨阶段 |
| 需求条目 | 12 | 超过 12 条说明这片承担了多个用户目标 |
| 组件节点 | 80 | 单轮生成的可靠上限，超过后细节开始退化 |

这些常量写在 `scripts/prd_slice.py` 顶部（`MAX_PAGES` / `MAX_CAPS` / `MAX_REQ` / `MAX_NODES`），
**改脚本即可调整，不要在文档里另立一套**。超限时 `plan` 与 `check` 都会报 ERROR。

---

## 4 切片计划（阶段④的产物）

写进 `shaping/slices.json`，它同时是**卡点 B 的确认对象**（用户确认的是切片清单，不是一个模糊的"板块顺序"）。

```jsonc
{
  "schema": "xx-prd-slices/1",
  "unit": "user-story",
  "slices": [
    {
      "id": "s-01",                       // s- 前缀，全局唯一
      "title": "采购员提交请购单",
      "actor": "u-buyer",                 // 主角色（多个角色说明该拆）
      "goal": "把车间提的需求提成一张可审批的请购单",
      "task": "t-1",                      // 对应 tasks[] 里的业务任务
      "pages": ["page-pr-list"],          // 只能属于一个切片
      "capabilities": ["cap-pr-submit"],  // 一条命令只有一个主页面
      "entities": ["PurchaseRequest"],
      "acceptance": ["REQ-PR-001"],
      "dependsOn": [],                    // 依赖的切片，必须无环
      "status": "pending",                // pending → done
      "estimate": { "pages": 1, "requirements": 1, "nodes": 45 }
    }
  ]
}
```

校验：`python3 scripts/prd_slice.py plan shaping/slices.json`

会拦住：页面/命令被两片同时认领、依赖成环、超上限、缺字段、多角色切片（WARN）。
通过后输出建议执行顺序（拓扑序）。

### 切片顺序怎么定

- **先纵向走通一条最薄的完整路径**：能提交就行，不审核、不统计。它证明数据模型与主流程成立。
- **再按状态推进加厚**：审核 → 驳回 → 撤销 → 批量。
- **配置类、统计类放最后**：它们依赖前面确定的字段与状态。
- 每片必须能在**已有切片基础上**独立验证；依赖前面的，写进 `dependsOn`。

---

## 5 逐片交付循环（阶段⑤）

一次只做一片，六步走完再下一片：

```
1) 读本片范围：slices.json 里这一条的 pages / capabilities / acceptance
2) 写片段文件：slices/s-01.json（只含本片的页面、需求、命令、状态机增量）
3) 单片自检：prd_slice.py check slices/s-01.json --plan shaping/slices.json
4) 合并：prd_slice.py merge slices/*.json -o XX-PRD.data.json --plan shaping/slices.json
5) 整份校验：validate_prd_json.py XX-PRD.data.json
6) 标记完成：prd_slice.py done s-01 --plan shaping/slices.json
```

**每步都是硬要求**：第 3 步不过不合并，第 5 步有 ERROR 不进下一片。
单片阶段允许出现「引用了别的切片的页面」这类跨片错误，**合并后必须为 0**。

> 一轮只交一片。想"顺手把下一片也写了"是质量衰减的开始。

---

## 6 单片产出格式

片段就是一个**缩小版 data.json**：顶层键与正式产物一致，只是内容限于本片。

```jsonc
{
  "sliceId": "s-01",
  "meta": { "schemaVersion": "1.1", "productName": "采购中台" },
  "product": { "name": "采购中台" },
  "users":        [ { "id": "u-buyer", ... } ],
  "modules":      [ { "id": "m-purchase", "pageIds": ["page-pr-list"] } ],
  "pages":        [ { ... } ],          // ≤ 4
  "capabilities": [ { ... } ],          // ≤ 6，且都在本片清单里
  "requirements": [ { ... } ],          // 每条 acceptance ≥ 2
  "stateMachines":[ { ... } ],          // 只写本片用到的状态与转移
  "dataModel":    { "entities": [ ... ] }  // 只写本片新增的字段
}
```

关键点：

- **`meta` / `product` 只在第一片写**，后续片段省略；两片写得不一致会被合并判错。
- **`dataModel` 是增量**：同名字段重复声明没关系，字段类型冲突会报错。
- **`modules[].pageIds` 可以各写一半**，合并时取并集。
- **`contract.actor` 必须是数组**（`["u-buyer"]`）。写成字符串会被容器按字符遍历，
  校验器会报一串"`n` 不在 users 中"的错 —— `check` 已提前拦截这条。
- **`contract.submitBoundary` 只能是 `single` / `staged` / `none`**，不是自由文本。
- **`contract.owns` 里的命令必须属于本片**，跨片会报错（一条命令只能有一个主页面）。

---

## 7 合并规则

`prd_slice.py merge` 按 id 合并，冲突就报错而不是"后者覆盖前者"：

| 类型 | 规则 |
|---|---|
| `pages` / `requirements` / `capabilities` / `stateMachines` / `tasks` | 同 id 内容必须完全一致，否则 ERROR |
| `modules` | `pageIds` 取并集，其余字段必须一致 |
| `dataModel.entities` | 按 id 合并，`fields` 按 name 去重；同名字段类型不同 → ERROR |
| `meta` / `product` | 多片声明必须一致 |

**为什么不允许覆盖**：合并冲突往往意味着两片对同一个对象的理解不同（比如同一条命令在两片里
`from` 状态不同）。静默覆盖会把这种分歧埋进产物里，直到评审才炸。

合并后**必须跑一次 `validate_prd_json.py`** —— 跨片引用（`entryFrom`、`interactions.navigate`）
只有合并后才完整。

### 跨片引用约定

- 允许引用**本片或更早切片**（`dependsOn` 链上）的页面
- 不要引用后续切片的页面：那片还不存在，会让当前片无法独立验收
- 真的需要"做完 A 才能进 B"的跳转，在 B 切片里补 `entryFrom`，不要反向写

## 8 反例

1. **按模块切片**：「用户管理」「订单管理」「报表管理」—— 每片都跨角色跨阶段，等于没切
2. **按技术层切片**：先做全部列表页，再做全部表单 —— 每片都走不通，无法验收
3. **一片塞两个角色**：采购员提交 + 经理审批放在一片，两套权限逻辑混在一起
4. **切片只写页面不给命令**：验收时"能看不能用"，命令策略没地方落
5. **跨片引用后续页面**：`entryFrom` 指向还没做的页面，当前片打开就是死链
6. **合并靠覆盖**：发现冲突就改后者，两套理解都留在产物里
7. **跳过单片校验直接合并**：把 4 片的错误攒到最后一起改，改动互相牵连
8. **一次交三片**：省下的那点轮次，会在评审时以"这页怎么和那页对不上"还回来

## 9 自检（交付每片前）

- [ ] 这片只有一个主角色；出现第二个角色时已写清它是"协作"还是该拆
- [ ] 主路径能从入口走到结果，不需要等下一片才"通"
- [ ] 页面数 / 命令数 / 需求数 / 节点数都没超上限
- [ ] 每条需求 ≥2 条验收，且覆盖了非法路径（状态不符 / 权限不足 / 并发冲突）
- [ ] 每个页面都有 `contract`，`owns` 里的命令都属于本片
- [ ] 每个页面都有 `type:"flow"` 的主流程图，判定出边带 label
- [ ] 每个页面至少一个状态带 `vars` 默认值（单独打开能渲染）
- [ ] 本片新增字段已进 `dataModel`，类型与枚举候选值写清
- [ ] `check` 通过、合并后 `validate_prd_json.py` 无 ERROR
- [ ] `done` 已标记，下一片才开工

---

## 10 与流程闸门的关系

切片不能单独用，它挂在闸门后面：

```
卡点 A 批准（需求 + 行为模型确认）
   → 写 shaping/slices.json → prd_slice.py plan → submit plan
   → 【卡点 B 确认切片清单】
   → 逐片：check → merge → validate → done
   → 全部 done 才能 guard export
```

`prd_flow.py guard export` 会检查切片是否全部 `done`，
所以"先导出一个看看"这条路是被堵死的 —— 这是故意的。
