# 12 · 视觉标准（可判定条款）

> 本文件是 XX-PRD 的**视觉判决书**。它的存在理由只有一条：
> 「页面看起来行不行」过去的答案是"看的人说了算"，现在必须是"量出来的数说了算"。
>
> **它不描述风格，它描述下限。** 每一条都写成「怎么量 / 阈值多少 / 正例 / 反例」。
> 一条条款如果没法用一条命令或一段 DOM 测量给出红绿，它就不该出现在这里 —— 请写进 `guide.html` 的说明文，不要写进本文件。

> 上表 14 行对应 `tests/check_ui_shape.py` 里的 V / T / W / S / L / C 六组。**没有豁免式 SKIP** —— 六组判据在任何视口宽、任何产物上都要给出结论，**不因「判不了」而跳过**；判不出就是口径错。**但「分母为 0」与「判不出」是两件事**：`S-02` 没有单行数据行、`P9` 没有任何一组 ≥2 行，那是**本来就没有可比基数**，走条件式 `SKIP(<条件与实测值>)`，条件写在 `value` 里、白名单只认条件不认 id（见 §1 的 `SKIP` 通用条款）。**把这两件混成一件，两边都错**：一律禁 SKIP → 空分母页上恒红、闸门恒非零；一律允许 SKIP → 又回到「判不了就跳过」。
>
> **P 组的 SKIP 若存在，必须带条件**：`P2a SKIP(行数 6 < 14，total 未声明)` —— 允许 SKIP **当且仅当**「示例数据行数 < 判据所需最少行数」**且**（该页**无分页器** 或 分页 `total` < 所需行数）。若 `total ≥ 所需` 而行数不足 → **`P2a INCOMPLETE(INSUFFICIENT_ROWS) total 342 ≥ 14，行数 6`**，不是 SKIP。**不区分「夹具」与「交付产物」**：同一条规则、两种结论，靠事实分 —— 只打 `SKIP`、或按「谁提供的文件」定去留，都是把判据删掉的前身（身份判定还会教人「把文件挪到 `examples/` 下」，那就是绕闸门）。**条件式 `SKIP` 在名单内不构成失败**：`P2a`/`P2b` 按上面条件跳过时，**这一次运行**仍可以是 `RESULT PASS` —— `PASS` 只要求**该次运行的范围内**「没有红、没有 `INCOMPLETE`、没有白名单外的 `SKIP`」。**这半句不能省，也不能读成全量模式能 `PASS`**：全量默认目标里有登记红的样本（`example-05` 18 条），`PASS` 结构上不可得（见下一条）。把「样本只有 6 行」读成「这门不可能绿」，与把 `SKIP` 读成失败是同一类误读 —— 下一步必然是把验收改成「→ `SKIP`」，也就是把「门能有绿的一天」这条唯一验收换成同义反复。`total` 是现成的（P13 已在读 `total=342`，不必加字段），它正是 `REJECT.md:116`「行数可被少造数据作弊」的正面回答：**不是不能少造，是少造会被 `total` 抓住**。**P 组有自己的 TOKEN 集**（目前一个：`INSUFFICIENT_ROWS`），与 §1 的 `CONTENT_ZERO` / `PARENT_INVISIBLE` / `NAV_OUT_OF_RANGE` **并列但不混用**；新增必须在这里登记，不许临时起名。打的必须是**该判据自己的**「所需最少行数」（`P2a` 与 `P2b` 不同，`P2b` 还按视口分档），**不许用一个共享常数** —— 否则同一份输出里 SKIP 行写 `6 < 9`、INCOMPLETE 行写 `≥ 14`，两行互相打脸。这条规矩要防的第一种人不是执行者，是**照抄工具输出写文档的人**：全量模式的 INCOMPLETE 结论行把**行数**印成了「条判据」（2 判据 × 2 档 = 4 行，文案却写「4 条判据」），照抄就会得出「`P2b` 的分母也是 14」—— 结论错得看不出来，因为两档的实际所需本来就不同（9 / 12）。**任何「分母是多少」的问题，只认判据自己的 need，不认结论行里的汇总数。**输出形态固定为**括号里先是 TOKEN、再是中文读数** —— TOKEN 供断言（`check_reject` / `--selfcheck` 按 **TOKEN 相等**比较，改一个汉字不影响断言），中文供人读。**不许只写中文「造少」**：那样断言只能做字符串包含，改一个字就失效。

> **本文件判的范围（DoD 11）**：形态判据判的是 `example-06-dense-list.json` **这一个验收夹具**，**不判全部示例**。全量模式（不带参数）的 `RESULT INCOMPLETE` 是它对某个示例的**真实答案**，**不得读成「门不通过」**；反过来，门绿也不代表全部示例达标。理由与 `INV-13` 同源：**门的绿 ≠ 产物合格** —— 门判的范围与全量判的范围是两个结论，不许互相替代。
>
> **全量模式的结论行不是达标信号。** 它的最后一支是 `RESULT PASS if 红数 == 0 else FAIL`（前面还有 `INCOMPLETE` 两支会先接管），所以只要还有**登记红**的样本（`example-05` 在 `EXPECTED_FAIL` 里登记了 20 条）留在默认目标里，全量模式就**不可能是 `PASS`** —— 把样本数据改对也一样，改的只是「哪条红」，红数不会归零。因此判「这一轮达标」看的是三件事，不是那一行的颜色：**① V8 的 FAIL 集与期望名单逐条相等；② 不出现任何 `INCOMPLETE`；③ 不出现 `SKIP-OUT-OF-WHITELIST`**。`RESULT FAIL` 只说明「有东西红了」，说明不了「红的是不是该红的那几条」—— 后者只有 V8 能回答。**不知道这一条的人，下一步动作必然是把全量模式改到 PASS**；结构上做不到，最后只剩 `continue-on-error`，与「恒红的门等于没有门」是同一条路。同理，**禁止把 `example-05` 摘出 `default_targets()`** —— 那是把登记红样本踢出覆盖，拿覆盖面换结论颜色。
>
> **最后一列「执行者」写的是现状，不是计划**，取值只有三种：`shape` = `check_ui_shape` 已接线 / `release` = 交付闸门 / `人工` = **当前无自动判据**（人工核，且**不许因此落 PASS**）。接线后把它改回 `shape`，**不许先把 `shape` 写上再补代码** —— 那一列就是「假约束」的可视化。截至 2026-10-27：V/T/W 九行与 **S-01、S-02a/S-02b** 是 `shape`；L-01/L-02/C-01 三行与 §6 的 C-02、§7 的 A-01~A-03 仍是 `人工`（L 组随 I-09 第三阶段，C-02/A 组登记在 **XX-044**，先于 XX-043）。
>
> **状态只有三种，且必须预先定义**：`PASS` / `FAIL` / `INCOMPLETE`。`INCOMPLETE` **只在「量具自己不可信」时出现**（V-01：导航宽越界、父节点不可见、`clientWidth=0`），它既不是绿也不是红 —— **记成 PASS 就是静默绿，记成 FAIL 就是把量具 bug 算到产物头上**。除这三态外不许执行者现场发明第四种状态。
>
> **`SKIP` 不是第四种结论，它是「这一条不适用」的标注 —— 因此必须带条件。** 形态固定为 `SKIP(<条件与实测值>)`，例：`SKIP(有效数据行 0 < 2，无表格数据行)`、`SKIP(无任一行盒组 ≥2 行：单行 1 / 多行 1 / 行盒 0 的 0 行量不到)`、`SKIP(分母 0：无单行数据行…)`。**不许写成 `value="—"` 而把条件塞进 `note`** —— 断言只读 `value`，`note` 是给人看的；`skip_allowed()` 也只认**条件**、不认 id（静态名单只留给「结构上永远不适用」的 `P8`/`P13`/`P17`）。**只把 id 加进名单，等于让这条判据在任何原因下都免检**，那是「少造几行就换一个 SKIP」的通行证。写不出条件的 `SKIP`，说明「这一页为什么不判」答不上来 —— 那缺的不是措辞，是判据。
>
> **本文件只有两个执行者，`ERROR` 不是本文件的词。** 运行时判据由 `tests/check_ui_shape.py` 判（`PASS` / `FAIL` / `INCOMPLETE`），交付闸门由 `scripts/check_release.py` 拦（I-09 第三阶段接线）。`ERROR` 是 `scripts/validate_prd_json.py` 的输出词 —— 它**只读 JSON、读不到字体度量与渲染结果**，所以本文件里「靠实测宽度 / 实测行盒 / 实测色值」立起来的条款，一条都不可能由它判定。**凡判据正文里出现 `ERROR`，就是漏写了执行者**：改成「由 ×× 判」，或写明「当前无自动判据」——**写一个不存在的 ERROR 比写错阈值更贵**，模型会以为这条已经强制了，于是把缺陷交给一个不存在的闸门（本段与 §9/§10 的说明文字里出现该词不算，那里是在讲这条规矩本身）。
>
> **本文件里每一条都必须能回答「谁判的」**，且答案只有三种：`check_ui_shape`（已接线）/ `check_release`（交付闸门）/ **当前无自动判据**（人工核，且**不许因此落 PASS**）。未接线的条款在正文里写明，不许用 `ERROR` 冒充已强制。
>
> **表里没有「表头折行」，但有「表头被裁」（T-04）—— 这两个不是一回事。** `white-space:nowrap` 防的是**折行**，不防**裁切**：容器 `index.html` 对 fixed 表的 `th` 同时给了 `overflow:hidden; text-overflow:ellipsis`，于是内容超出盒子时，失败形态从「折成两行」变成「被裁掉并显示省略号」。
>
> 判「这条判据能不能立」的标准不是「当前样本红不绿」，而是**「能不能找到一个输入让它红」**：
> - 折行：现在任何宽度都不会折（`nowrap` 无条件）→ **找不到输入 → 恒绿 → 撤**；
> - 裁切：把 `example-06` 的 `序号` 改回 48 就红 → **找得到输入 → 可判 → 立（T-04）**。
>
> 上一轮撤掉折行是对的，但不能因此把裁切一起排除 —— 撤的依据是「结构上恒真」，不是「表头这一族都不判」。

## 0. 效力与冲突：AntD 是实现基线，不是审美上限

### 0.1 定位

| 层 | 内容 | 谁说了算 |
|---|---|---|
| **实现基线** | Ant Design 5 的 token（`--ant-*`）、组件语义、交互惯例 | 本文件未覆盖处，**默认照 AntD**；这样产物与用户既有的后台心智一致，且不需要解释"这个按钮为什么长得不一样" |
| **判决层** | 本文件的 V/T/W/S/L/C/Q 条款 | **优先于 AntD**。AntD 的默认值与下面任一条冲突时，按本文件改 |
| **表现层** | 具体颜色、圆角、图标、文案 | 作者自由，但不得突破判决层 |

**一句话**：**AntD 给你默认值，本文件给你下限，两者冲突取本文件。**

### 0.2 冲突时怎么办（三步，不许跳）

1. **先确认冲突是真的**：拿 `getComputedStyle` 量出来，不靠"感觉 AntD 这样更规范"。例：AntD 的 `Table.size='middle'` 行高 48，与 S-02「`tr ≤ 34`」冲突 —— 这是**真冲突**，因为 48 > 34 是实测数。
2. **按本文件改**，并在 PRD 的「交互说明」里写一行记录：`冲突：AntD 默认 size=middle（行高 48）vs 12 §4 S-02（≤34）；采用 size='xs'`。
3. **若改不动**（容器能力不支持），写成 `notApplicable` 并在 PRD 里留一条 `openQuestion`，**不许静默按 AntD**。静默按 AntD 的后果是：判据在下次评审时才红，而那时已经画了 7 个页面。

### 0.3 本文件**不管**什么

- 不管配色选了哪几个色（只管色彩**种类数**，见 C-01）；
- 不管信息架构是否合理（那是 `10-page-decomposition.md`）；
- 不管选哪个容器（那是 `08-container-choice.md`）；
- 不管文案好坏（那是 `03-prd-structure.md`）。

**划清边界的理由**：一份规范只要开始管主观偏好，它就再也判不出来了 —— 因为偏好没有反例。本文件只判**可测量的几何与计数**。

## 1. 视口与内容宽

### V-01 宽度必须与视口**闭合**：归因差（主）+ 父节点铺满

> **先读这一段：`① + ② + ③` 不是判据，是恒等式。** 记 `Wc = content.clientWidth`、`p = paddingLeft + paddingRight`、`b = content 左右 border`：
>
> ```
> ① = Wc − p        ② = 父.offsetWidth − (Wc + b)        ③ = p
> ① + ② + ③ = 父.offsetWidth − b        ← 与视口无关
> ```
>
> **所以「三数之和 vs 视口」判的其实是「父节点有没有铺满视口」，对「内容被压窄」完全免疫**：`max-width:1024`、`props.style.width:"1080px"` 这类输入里父节点没变，**闭合差恒为 0，结构上抓不到**（老刘实测：N-a / N-b 抓不到，N-c 抓得住）。这条式子不写清语义，就会一直判着另一件事却挂着「内容适配」的名字 —— 而 `max-width` 与写死宽正是 Owner 第一条要求的主要形态。
>
> **因此 V-01 有两条判据**：判据①**归因差**问「丢掉的宽度是不是被导航合法占走的」，判据②**父节点铺满**问「父节点有没有被换小」。两个数虽同源，但**不能合并、也不能都当判据**：`闭合差 ≡ −(铺满差)`，同一件事写两遍就是重复计数（见下「符号怎么报」）。

| 项 | 内容 |
|---|---|
| **三个加数（只作展示，不作为判据）** | ① **内容宽 = `content.clientWidth − paddingLeft − paddingRight`**（即 **content-box 宽**，实现里的 `contentBoxW`，**不是 `clientWidth`**）；② **页内导航宽 = `父节点.offsetWidth − content.offsetWidth`（减法式，含 padding）**；③ 内容左右 padding = `.ant-content` 的 computed `paddingLeft + paddingRight`。三者相加仍要打进报告（说明「宽度去哪了」），但**结论由下面两条判据给** |
| **①用 content-box、②用 `offsetWidth`，这个混用是刻意的** | `clientWidth` **已经含 padding**，所以 ① 必须先把 padding 减掉，③ 才把 padding 加回来；② 的 `offsetWidth` 含 padding 与 border，减法拿到的「被横向占走的宽度」才是完整的。**若 ① 直接取 `clientWidth`，padding 就被算两次**：教材 `1232 + 208 + 48 = 1488`，@1440 差 **48 → 教材被自己的判据误红**。要「把两条统一成一个口径」之前先看这一行 —— 统一的结果只会是其中一条错 |
| **口径自证（只留能红的那一半）** | `① + ③` 与 `content.offsetWidth` 比，**差 ≤ 3px**；超出就打 `BORDER_OR_SCROLLBAR` 并附 `①` / `③` / `offsetWidth` 三个数。**它能红**：若 ① 误取 `clientWidth` 原值（v5 那个错），教材得 `1232 + 48 = 1280`，而 `offsetWidth = 1232`，**差 48 立刻现形**。**绝不写 `① + ③ = clientWidth`** —— ① 减掉的 padding 正是 ③ 加回来的，那是**定义上的恒等式，永远为真**，属于「必然为绿的判据」，比没有判据更危险（会让人以为这一栏查过了） |
| **减法式 / 真实导航 / 无条件求和是三件事** | ② 的语义是「被谁横向占走了」→ 用**减法**（`父宽 − content.offsetWidth`），两种布局都成立。**真实导航**是判据①的比对面，按**几何**取（纵向重叠 + 水平不相交 + 非定位，见下「真实导航怎么算」），**必须带这三条约束**：CAPA 的兄弟是 `div.ant-header`（宽 **1440**，是上面一整行的页头），**无条件求和**得 `1392 + 1440 + 48 = 2880`、差 1440 → **一份完全合格的产物被判 FAIL**。教材 `example-06` 的兄弟恰好是 `div.ant-sider`(208)，求和才碰巧对 —— 所以求和只有在「先按几何筛过兄弟」之后才可用 |
| **父节点怎么定** | **父节点 = `content.parentElement`**（**直接父盒**；为 `null` 时取 `document.documentElement`、宽用 `clientWidth`，因为 `documentElement.offsetWidth` 含滚动条、会引入 15px 级误差）。量 `offsetWidth`（**不是 `scrollWidth`**）。**主口径不用 `offsetParent`** —— 它的定义是「最近的**已定位**祖先」，静态父盒会被它跳过（`position:fixed` 浮层包裹时跳得更远），而「被谁横向占走了」问的是**直接父盒** |
| **`offsetParent` 只作交叉校验** | 与 `parentElement` 不一致时**以 `parentElement` 为准**，两个 `tag.class` 都打进报告标 **`PARENT_MISMATCH`**。不一致本身是信息（说明这页有定位祖先或浮层包裹），**不是判据、不是 INCOMPLETE**，结论仍按 `parentElement` |
| **父节点不可见 → INCOMPLETE** | `父节点.clientWidth === 0`（`display:none`、未挂载、被折叠）→ `INCOMPLETE(口径错) 原因=PARENT_INVISIBLE`，**不许落 PASS/FAIL** |
| **输出必打父节点身份** | 报告行必须含 `父节点=<tag.class> 宽=<n>`，**不许只打导航宽**。只打一个数时「父节点选对」与「父节点选错」在文本上无法区分 —— 而人看到 INCOMPLETE 通常当成工具坏了，不会想到是量错了，这件事只能靠这行字解决 |
| **两档各判** | 1440×900 与 1600×1000 **各判一次**，**两条判据、任一档、任一超差即 FAIL**；两档读数必须分开打，不许合并、不许取平均（`N-e` 的「两档增量」只是诊断打印，不参与 PASS/FAIL，见下） |
| **导航宽只判负侧，否则报 INCOMPLETE** | 判据只有半边：`导航宽 ≥ 0`。**上界写不得** —— `父宽 − content.offsetWidth` **就是导航宽本身**（减法式的定义），代入后 `导航宽 ≤ 导航宽` 恒真、`导航宽 > 导航宽` **恒假**：写上去的是一条**永不触发的分支**，它会一直显示 PASS，因为根本不触发（老刘实测）。负值（`content.offsetWidth > 父盒.offsetWidth`，内容比父盒宽）说明**量具选错了父节点或取错了元素** → 报 **`INCOMPLETE(口径错) 原因=NAV_OUT_OF_RANGE`**，**既不是 PASS 也不是 FAIL**。理由：量错时差可能恰好是 0，那就是「静默绿」；三种状态必须由设计者预先指定，不许执行者现场发明 |
| **产品态** | 右栏 PRD 面板未挂载或 `display:none`；标注层关闭；画布 zoom = 100%；**产品自身**的左侧导航保留（它是加数②，不是误差项） |
| **评审态** | 同屏三栏（模块导航 + 内容 + PRD 面板）。**两条判据在评审态都不成立** —— PRD 面板不是产品的一部分，加进去就等于给工具外壳买单。评审态**只记录内容宽，不代入本条任何一条判据** |
| **判据① 归因差（主）** | `abs(减法导航 − 真实导航) ≤ 8px`。**问的是「丢掉的宽度是不是被导航合法占走的」**：减法导航比真实导航大，说明有一段宽度既不是内容、也不是导航、也不是 padding —— 那就是 `max-width` / 写死宽 / 外层壳。报告打 `差 = 减法导航 − 真实导航`，**带符号**：正 = 没人认领的宽度（N-a 208 / N-b 152 / `flex:0 0 1184`@1600 160）；负 = 「父宽 − 内容」装不下真实导航（父盒选错，或导航是覆盖式/绝对定位），**同样 FAIL**，但必须把两个数都打出来 |
| **判据② 父节点铺满** | `abs(父.offsetWidth − b − 视口) ≤ 8px`（`b` = content 左右 border，通常为 0，**必须打出来**）。**问的是「父节点有没有被换小」**：换一层固定宽壳（N-c）只在这里红。`差 = 父.offsetWidth − b − 视口`，负 = 父盒比视口窄。**它与「三数之和 vs 视口」是同一个数**（差 ≡ 视口 − 父 + b），只是把符号写正了 —— 所以只留这一条，三数之和只作展示。**居中 `max-width` 的整站外壳不豁免**（见下）。**可达性提示**：铺满差在**产物空间里恒为 0** —— `Layout` 不消费 `width`/`style`（JSON 层换不了壳），CSS 又包不出一层 div（`margin` 只会让归因差红），所以它唯一的可达证据是 `fixture-nc-manual-shell.html`，见 §V-02 |
| **视口口径** | **`window.innerWidth`（含滚动条）**，与 `父.offsetWidth` 同口径。**不用 `documentElement.clientWidth`** —— 有纵向滚动条时它恒小约 15px，一屏一屏全报超标，比静默绿更难查 |
| **真实导航怎么算（几何定义，不看 class）** | 满足以下三条的**同级兄弟**的 `offsetWidth` 之和：① 与 content **纵向重叠**（`r.top < c.bottom && r.bottom > c.top`）；② 与 content **水平区间不相交**（`r.right <= c.left + 1` 或 `r.left >= c.right - 1`）；③ `position` 为 `static` / `relative` / `sticky`（**排除 `absolute` / `fixed`** —— 抽屉与浮层不参与流式布局，算进去会凭空多一块）。**为什么不用 class**：若产物用自定义元素做导航（不带 `.ant-sider` / `.ant-menu`），class 判定会把真实导航算成 0 → 归因差 = 减法导航 → **合格产物被误红**。几何判定下：教材 sider（纵向重叠 + 水平不相交）→ 208；CAPA 的 `ant-header`（**纵向不重叠**，在上方一整行）→ 0；自定义导航元素 → 照样算进去；打开的抽屉（`absolute`）→ 排除 |
| **找不到导航是正常的，不是 INCOMPLETE** | 内容区**没有任何纵向重叠的兄弟**时，真实导航 = 0 是**正常形态**（全宽内容区，CAPA 就是），**不许因为「没找到导航」报 `INCOMPLETE`**。三态里唯一该报 `PARENT_INVISIBLE` 的是父节点不可见那一种 —— 把「没有导航」当量具失败，会让所有全宽页面集体无法出结论 |
| **导航侧 `MISMATCH` 取消**（父节点侧保留 `PARENT_MISMATCH`） | 真实导航成为判据的一部分之后，它与减法式的差异**不再是提示，就是红本身**。报告里两个数照打（`导航208[减法416 / 真实208]`），**不再有 `MISMATCH` 标签**，也不要把它塞进 `INCOMPLETE` 的 TOKEN 里。`PARENT_MISMATCH` 是另一件事（`parentElement` 与 `offsetParent` 不一致），只标事实 |
| **三数之和（展示项）** | `abs(视口 − (内容宽 + 导航 + padding))` 仍要打，**但结论不读它**（恒等于父宽，见本节开头）。它的符号语义保留：正 = 有一段宽度既不是内容也不是导航也不是 padding；负 = 三数之和超过视口 = **横向溢出**（竖排/宽度失控时的伴生现象，与 `P8` 的接口不变：溢出的量与位置由 `P8` 判，V-01 只给「父盒比视口宽」这个数） |
| **为什么是「与视口闭合」，不是百分比** | 产品有没有页内导航，会让内容宽占视口的比例天生差 208/1440 ≈ **14.4%**。任何一个百分比都只能二选一：卡住有导航的（教材 `example-06`@1440 只有 **82.2%**，会误红），或放过没导航的（CAPA 两档 96.7% / 97.0%，阈值定 80% 对它毫无约束）。**这里没有公约数。** 闭合式把「少掉的那 208」显式加回去，不需要为「有没有导航」设特例 |
| **8px 从哪来** | 两次 `clientWidth` 取整（各 ≤1px）+ 滚动条与边框取整（≤2px）+ 亚像素累计 + **content 自身边框**（`offsetWidth` 含 border，`clientWidth` 不含；两边各 1px 就是 2px）。**它不是调出来的容差**：超过 8px 就说明有一块宽度既不是内容、也不是导航、也不是 padding —— 那正是「内容区写死 1200」的形态 |
| **正例** | `example-06`@1440：内容 1184 / 减法 208 / 真实 208 → **归因差 0、铺满差 0**；@1600：1344 / 208 / 208 → 0 / 0。CAPA@1440：1392 / 0 / 0 → 0 / 0；@1600：1552 / 0 / 0 → 0 / 0。**两个差都要打、都要 ≤8；缺任一个数即未完成** |
| **反例** | **① `max-width:1024`**：内容 976、减法 `1440−1024 = 416`、真实 208 → **归因差 208** FAIL；**铺满差 0**（父节点没变 —— 这正是「只判父节点」的式子在 N-a 上恒绿的原因）。**② `props.style.width:"1080px"`**：1032 / 360 / 208 → 归因差 **152** FAIL。**③ 外层 `1100` 壳**：1052 / 减法 0 / 真实 0 → **归因差 0**，但铺满差 **340** FAIL（**只有判据②能抓**）。**④ 兄弟无条件求和**（CAPA）→ 真实导航算成 1440、归因差 1440 → 误红（纵向重叠约束修掉的那一类）。**⑤ `zoom:.9`** → 两个差都是 0，只能靠 N-d |

> **判据② 把「居中 `max-width` 的整站外壳」判红 —— 正确，不豁免。** 我们的产物是列表页 / 详情页 / 工作台，是**干活的地方**，不是阅读页：表格工作区居中收窄，正是 Owner 说的「页面宽度没按屏幕适配」。
>
> > **本条的适用前提是工作页（列表 / 详情 / 工作台）。阅读型页面的居中栏宽不在本条范围内；若需要，按页面类型单开条款，不给全局容差。**
>
> 这一句限定是为了让下一个人改的时候**必须改条款**，而不是把 8px 调大 —— 一旦允许「阅读页豁免 × 容差放宽」，表格页的 340px 也会跟着被放过。

> **三数之和的 `差` 仍要打、仍带符号，但它不是判据**：`差 = 视口 − (内容宽 + 导航 + padding)`，而它**恒等于 `−(铺满差)`** —— 同一个数写两遍就是重复计数（那会让「一条病红两次」），所以**判据只读铺满差，三数之和只作展示**，用来解释「这块宽度去哪了」。
> **负号不许抹**：把 `−16` 抹成 `0`、或改成 `max(0, diff)`，就等于把「父盒比视口宽」这条信息丢掉 —— 而它是横向溢出的唯一来源。
> **这是 V-01 与 `P8` 横向溢出的接口**：V-01 只回答「父盒/内容相对视口多了或少了多少」，**溢出多少、往哪溢**由 P8（`table.scrollWidth > clientWidth + 1`）管。两处必须同时红，**不许出现 V-01 红而 P8 绿、或反之** —— 同一个屏幕状态不能有两种结论。

> **N-c 那一行的归因差是 0，必须单独立出来看**：壳一包，content 与 sider 就不再是兄弟，减法导航与真实导航同时变 0，**两个数互相抵消**。它只能靠判据②抓 —— 谁说「归因差也覆盖 N-c」，就是没算这一格。同理，N-c 的**三数之和正好等于壳宽 1100**，再次说明那三数只反映父节点。
>
> **N-e 是诊断打印，不判红、不占编号、缺陷计数 0。** 它原来那条式子（两档内容宽增量 = 视口增量）只有一个输入能单独触发：**两档 padding 不同**（`@1440 padding:24`、`@1600 padding:30` → 内容宽增量 148 ≠ 160）。而「屏幕变宽多留白」是**正当设计**，不是缺陷 —— **一条只在合法产物上红的判据，会教人去加容差**，然后把真缺陷一起放过。它想抓的「两档被写成常数」已经由**归因差 @1600** 抓住（内容锁 1184 → 减法 `1600−1184=416`、真实 208 → 归因差 208 红，见上表），剩下的独立触发能力全落在该绿的输入上。报告保留这行打印：`N-e 诊断: 内容宽@1440=1184 @1600=1344 增量160 / 视口增量160`（**不进 PASS/FAIL**）。将来若真要管「两档留白是否一致」，那是 §5 留白的事，**单独立条，别挂在 N-e 上**。
>
> **符号怎么报**：`归因差 = 减法导航 − 真实导航`（正 = 没人认领的宽度；负 = 父宽装不下真实导航，多为父盒选错或覆盖式导航）；`铺满差 = 父.offsetWidth − b − 视口`（负 = 父盒比视口窄）；`三数和的差 = 视口 − (内容宽 + 导航 + padding)`，**它恒等于 `−铺满差`，只作展示**。三个数都必须带符号打，不许取绝对值输出（`abs` 只用于比较）。

> **反例 A 为什么必须写进规范**：教材的兄弟恰好是 sider，求和看起来"能用"；CAPA 的兄弟是页头，无条件求和直接把一份合格产物判死。**这不是理论风险，是实现者拿两份样本一跑就会撞上的分叉**。减法式的语义是「被谁横向占走了」，与「旁边有谁」无关；真实导航只在**纵向重叠 + 水平不相交 + 非定位**这三条约束下才可以用求和 —— 三条件都得写，少哪条都会误红（少第三条，打开的抽屉会凭空多一块）。

**报告主行必须五段齐全：父节点身份、两个导航宽、两个差**：

```
V-01 1440 父节点=div.ant-layout 宽1440 内容1184 导航208[减法208 / 真实208] padding48 三数和1440 归因差0 铺满差0 (≤8) PASS ｜ 评审态 1074 不判
V-01 1440 父节点=div.ant-layout 宽1440 内容976  导航416[减法416 / 真实208] padding48 三数和1440 归因差208 FAIL(cause=N-a) ｜ 铺满差0
```
- 父节点身份在前（`父节点=<tag.class> 宽=<n>`），**它是「量对了没有」的唯一凭据**；
- 括号里是**减法 vs 真实**两个数（不是「校验值」），差异大于 8 就是红本身，**不再有 `MISMATCH` 标签**；
- **两个差都要打、都要与 8 比**；只打一个差的报告视为未完成（N-c 只有铺满差会红，N-a 只有归因差会红 —— 缺哪个就会漏掉哪一类产物）；
- 父节点选错或**导航宽为负（只有负侧；上界恒假，已删）** → 直接是 `INCOMPLETE(口径错) 原因=<TOKEN>`（`CONTENT_ZERO` / `PARENT_INVISIBLE` / `NAV_OUT_OF_RANGE`，只此三个），**这一行不许出现 PASS/FAIL**。

**三态，不是两态**：`PASS` / `FAIL` / `INCOMPLETE`。INCOMPLETE 只在「量具自己不可信」时出现。**不许把 INCOMPLETE 记成 PASS**（那是静默绿），也**不许记成 FAIL**（那会把量具 bug 算到产物头上 —— 与 I-07 P2a 的处理方式一致）。

**`INCOMPLETE` 的原因只有三个 TOKEN，输出固定形态 `INCOMPLETE(口径错) 原因=<TOKEN>`**：

| TOKEN | 触发条件 | 中文 |
|---|---|---|
| `CONTENT_ZERO` | 找不到 `.ant-content`，或其 `clientWidth === 0` | 内容区不可见 |
| `PARENT_INVISIBLE` | `parentElement` 为 `null` 且 `documentElement.clientWidth === 0`；或父节点 `clientWidth === 0` | 父节点不可见 |
| `NAV_OUT_OF_RANGE` | 导航宽 **< 0**（只有负侧；上界恒假，见本节「只判负侧」行） | 导航宽为负 |

- **只准这三个值**，不许「原因=父节点选错了」这类自由文本 —— **自由文本没法被断言，也就没法进基线**；
- 守卫按 **TOKEN 相等**断言，不按条数（条数相同而集合不同：`list` / `overdue` 各 21 条、集合不同，已经付过一次代价）；
- **`PARENT_MISMATCH` 不是 `INCOMPLETE`**：它只标「`parentElement` 与 `offsetParent` 指的不是同一个盒子」，结论仍按 `parentElement` 算、只是打出来。混进三态会让「量具不可信」与「这页有定位祖先」分不清 —— 后者根本不是错。**导航侧的 `MISMATCH` 已经取消**（差异大于 8 就是归因差的红，不再是提示）。

**为什么必须把评审态分开报**：评审态的 1074 = 1440 − 导航 − PRD 面板 − padding，差价是**评审工具的外壳成本**。把 74.6% 当产品宽度去卡，等于要求产品为一个它控制不了的侧栏买单 —— 上一轮 I-07 已经为此付过一次代价。反过来说，如果只报一个「内容宽」，两个人在两个态上量出两个数、得出两个相反结论，这条判据就永远吵不完。

**V-01 抓不住 CAPA，这一点必须写在前面**：CAPA 两档两条判据都绿（归因差 0、铺满差 0），**本来就过这条**；它的病在 `tableLayout:'auto'` 让列被压（W-00 / W-02）与 Tag 内宽不足（T-01 / W-01）。谁把「宽度按屏幕适配」当成 CAPA 的解法，就会改完这条然后发现缺陷一个没少。V-01 的职责只有一个：**挡住「有一块宽度既不是内容、也不是导航」的那类产物**。

**为什么不写「内容宽 = 866」**：866 是「评审容器把 PRD 面板摊开」之后的剩余宽度，它是**工具的排版状态**，不是产品的宽度。用工具的排版状态当产品的列宽预算，会让作者按一个假想宽度写布局，而用户在 1392 上看它 —— 这就是「页面宽度应按常见电脑屏幕适配」这条要求的真实含义。

### V-02 固定窄容器清单（`cause` 标签，每条都必须能红）

> **四类 `cause` 不是四条判据**：红由 V-01 的两条判据给，N-a~N-d 只回答「红在哪一类输入上」，写成 `FAIL(cause=N-a)`。**但每一类都必须有能红的输入** —— 造不出红的要写明「不可达」及原因（见 N-c）。**`N-e` 不在其中**：它是诊断打印，不判红、不占编号（理由见本节末）。
>
> **读数一律按 content-box + 两个差**。上一版那五行写的是 `n + 导航 + padding`，把 padding 算了两遍（`1024` 是 **border-box**，里面已经含 48 padding），与加数①的口径直接矛盾 —— 那是 D-4 在同一个文件里的第二次复发。

| 编号 | 形态 | 为什么禁 | 正例 | 反例（内容宽 / 减法 / 真实 → 两个差） |
|---|---|---|---|---|
| **N-a** | `.ant-content` 或其**任一祖先**的 `computedStyle.maxWidth` 是具体像素值，且**归因差 > 8** | 上限一旦写死，宽屏上永远不撑开 | 不写 `max-width`，或写 `max-width: none` | `max-width:1024` @1440：内容 **976**（`1024−48`）、减法 **416**、真实 208 → **归因差 208**、铺满差 0 → FAIL(cause=N-a) |
| **N-b** | `Content` / `Layout` 节点的 `props.style` / `style` 里有 `width:<n>px`，且**归因差 > 8** | 同上，且更难发现（藏在 JSON 里） | 让 flex 撑满 | `{"type":"Content","props":{"style":{"width":"1080px"}}}` @1440：**1032**（`1080−48`）/ **360** / 208 → **归因差 152** → FAIL(cause=N-b) |
| **N-c** | 内容区外层套固定宽容器（宽度由显式声明而非 flex 撑开），且**铺满差 > 8** | 换一层壳就绕过 N-a / N-b | 外层只做 `flex:1; min-width:0` | `width:1100px` 的 div **只包内容区** @1440：**1052**（`1100−48`）/ **减法 0** / **真实 0** → **归因差 0**、**铺满差 340** → FAIL(cause=N-c)。**本容器不可达**，见下 |
| **N-d** | 内容区被 `transform:scale()` / `zoom` 缩放（`zoom ≠ 1`、或祖先带非单位 `scale`） | 「缩出来看着宽」不是适配，是**伪造测量值** | 不缩放内容区 | `.ant-content{zoom:.9}` → 布局宽 `1184 ÷ 0.9 = 1316` 而 `clientWidth` 报 1184，**两个差都是 0** → **只能靠本条独立判红** |
| **N-e**（**诊断量，不判红**） | 两档内容宽的增量 vs 视口增量，只打印 `内容宽@1440 / @1600 / 增量` 与 `视口增量` | —（不判红、不占编号、缺陷计数 0） | `example-06` 1344−1184 = **160**；CAPA 1552−1392 = **160** | 内容区锁 `flex:0 0 1184px` → **红在归因差**（@1600 减法 368 / 真实 208 → 归因差 **160**），不写 `cause=N-e` |

> **N-e 为什么降成诊断**：那条式子（两档内容宽增量 = `1600 − 1440` = 160）**只有一个输入能单独触发它** —— 两档 padding 不同（`@1440 padding:24`、`@1600 padding:30` → 增量 148 ≠ 160），而此时归因差 0、铺满差 0。**「屏幕变宽多留白」是正当设计**，于是这条判据的独立触发能力**全部落在该绿的输入上**：它会教人给 8px 加容差，然后把真缺陷一起放过。它原本想抓的「两档被写成常数」已由归因差 @1600 抓住（见上表右列）。所以：**保留这行读数（它是解释用的），不进 PASS/FAIL、不占编号、缺陷计数 0**。若将来真要管「两档留白是否一致」，按 §5 留白单独立条。
>
> **N-d 为什么不能靠 V-01 代替**：缩放把布局宽与 `clientWidth` 读数解耦（`zoom:.9` 下内容盒实际布局宽 1316，而 `clientWidth` 报 1184），两个差恰好都被磨平。它是 V-01 的**补集**：一条判据挡不住「能改测量本身」的输入。
>
> **N-c 在本容器不可达 —— 必须写明，不许假装覆盖了。** 容器把 `Layout.props.style.width` 直接落到节点自己身上（于是走 N-b），**不生成中间壳**，所以产物空间内造不出 N-c。**但不可达不等于不验**：`--selfcheck` 里造一份 **`fixture-nc-manual-shell.html`（手写 HTML 壳，非容器产物）**——文件名必须标出这个性质，否则半年后会有人以为容器支持这种形状。断言要比对**两条式子**：`归因差 0 ｜ 铺满差 340`；只贴「340 红了」证明不了「归因差抓不到它」，而那个对照才是这条样本的价值（**能红的样本防的是回归，「不可达」记账防的只是遗忘**）。**`cause=N-c` 只允许出现在该 fixture 上**，容器产物里出现 `cause=N-c` 一定是分类错了。
>
> **这条 fixture 同时是「铺满差」唯一的可达证据，这一点必须写进条款。** 产物空间里判据② 恒为 0：JSON 层 `Layout` 不消费 `width`/`style`，CSS 层包不出一层 div（`margin:0 auto` 只会让内容变窄 → 归因差红，父盒宽度不变）。所以「判据② 在真实产物上验过」**是假的** —— 它只在 `fixture-nc-manual-shell.html` 上验过。写清楚这一点，下一个人不会把一个从未在真实产物上触发的判据当成已通过考验。`--selfcheck` 因此从 **23 条变 24 条**。
>
> > **通用纪律：每一条 `cause` 值，要么有输入能产出它，要么写明「不可达」及原因。** 永远产出不了的成因标签，与永远为绿的判据同样危险 —— 它会让人以为这一类被覆盖了。

## 2. 文本不得折行、也不得被裁

> 这一节是 Owner 第一条要求里最具体的一条（原话："至少二字字段不得在表格行内换行"）。
> **原话是意图，不是判据。** 下面三条把它翻译成"这段字渲染成了几行"。
>
> **判定范围先说清**：T-01~T-03 只判**短字段格子** —— ① `td` 内含 `Tag` / `Button` 的单元格；② 整格文本（去空白）≤ 6 个全角字宽的单元格。两者并集是分母，必须打出来（`短字段折行 33/39@1440`）。
> 长文本列不在本节：它们的值是句子，本来就该截断或换两行，规则见 T-02。**把长文本算进分母，分母会被稀释到 30% 以下，判据就废了。**
> **T-01 必须按档位分列计数**（`33/39@1440` / `7/39@1600`），**不许合并成一个「x/78」**：同一份产物在两档的折行数差 4 倍多（33 对 7），合并后「1600 档本来没事」会被读成「整体折行率下降」。理由与 T-04 的分母分列同源 —— **档位不是产物属性**。
> **T-04（表头被裁）是另一套分母**：`th` 文字 **1~6** 全角字的列。它不属于「短字段格子」，不要并进 33/39 里。

### T-01 短字段单元格不得折行

| 项 | 内容 |
|---|---|
| **判据** | 对每个短字段格子，取**承载文本的最内层元素**（`.ant-tag` / `.ant-btn` / 文本节点）建 Range：`r.selectNodeContents(el)`，把 `getClientRects()` 的 **`top` 四舍五入去重**，**不同的 top 个数 > 1** 计为折行。**阈值 0** |
| **为什么按 `top` 去重、不数 rect 个数** | `text-overflow:ellipsis` 下，被裁掉的尾巴在 Chrome 里会被切成**第二个 rect，但 top 相同**。数 rect 会把「被裁」读成「折行」：`example-06` 两列 `ellipsis` 会被读成 **19/20、20/20 全折行**，而它们其实是单行+省略号。**一条判据把另一种失败形态算成自己的红，就是不可判定** |
| **为什么要量最内层** | 单元格与 Tag 是两层盒子。量 `td` 的文本范围会把"Tag 一行 + 单元格第二行空着"混进读数；量最内层元素只回答一件事：**这段字排了几行** |
| **为什么用 Range** | 折行的单元格 `scrollWidth ≈ clientWidth`（文字宽度被限制在盒内、换行消耗），`scrollWidth > clientWidth` 在折行场景下**恒绿** —— 本项目最容易被写成假绿的一条判据 |
| **为什么不数 `offsetHeight`** | 高度受 padding / border / line-height 三重污染。I-07 的 R9 踩过：`tr.offsetHeight` 含 1px 边框，阈值 32 逼人去删边框 |
| **分母** | 输出必须是 `折行格数 / 短字段格数`（如 `33/39`），**只报"0 处折行"无效** —— 不报分母无法区分"没有折行"和"没查到格子" |
| **正例** | 「类型」列宽 72：cell padding 24 + Tag padding 14 + border 2 → Tag 内宽 32，`纠正` 自然宽 26 → 26 ≤ 32 → rects = 1 PASS |
| **反例** | 同一列在 `tableLayout:'auto'` 下被压到 62 → Tag 内宽 22 → 26 > 22 → rects = 2 FAIL（证据 §3.4 D2/D3）；1440 档整页 **33/39 折**、1600 档 **7/39 折** |

**Tag 的 14px 是硬扣除**：`Tag` 左右 padding 各 7px 吃掉 14px 内宽，这 14px 必须进 W-01 的 `needW`，否则"列宽看着够、字还是竖排"会反复出现。

### T-02 允许换行的三选一

| 声明 | 渲染结果 | 适用 | 反例（不允许的写法） |
|---|---|---|---|
| `ellipsis: true` | 1 行 + 省略号 + `title` 兜底 | 长文本、可截断、需要扫读 | 配了 `ellipsis` 但值没溢出（假省略号，P18 判） |
| `wrap: true` + `maxLines: 2` | 2 行 + 第 2 行溢出省略 | 必须看到前半句才能判断（如"不合格陈述"） | `maxLines: 3` 及以上（行高预算吃光 —— 两行以上的行**不进 S-02 的分母**，但三行会直接压掉首屏整行数 P2a/P2b） |
| 移出表格 | 进抽屉 / 详情 / 折叠区 | 真正的长文本（>60 字）、需要完整阅读 | 留在表格里靠"浏览器默认换行" |

**三者都无且渲染 ≥2 行 → 计入 T-02 自己的缺陷数**（分母 = 长文本列），**不要并进 T-01**。理由：给一个 Tag 列配 `wrap` 会让 T-01 与 T-02 同时变色，两个判据对同一次改动都报红，读报告的人无法判断该改哪一条。「靠浏览器默认换行」是本文件唯一**明确禁止**的排版方式 —— 因为它的结果不可预测（取决于列宽与字体），而不可预测等于不可判。

### T-03 行数上限

| 项 | 内容 |
|---|---|
| **判据** | 任何单元格渲染行数 ≤ 2；且 `td.getBoundingClientRect().height ≤ lineHeight × 2 + paddingY × 2 + 1` |
| **为什么要有这条** | T-02 允许 2 行，但如果 3 行也放过，T-01 就形同虚设（只是把"默认单行"改成了"最多三行"） |
| **正例** | `wrap:true, maxLines:2` 的单元格高 50（21×2 + 5×2 − 2）→ PASS |
| **反例** | 证据 §3.3 V3：`聚锐过滤格栅后物料取样检出铁含量 0.031%，超出内控 0.020% 上限，涉及 4 个批次` 占 3 行，把行高拉到 58 |

### T-04 表头不得被裁（0 容忍）

| 项 | 内容 |
|---|---|
| **判据** | 锚点 = **实际发生裁切的盒子**：自身 computed `overflow-x === 'hidden'`（或 `clip`）**且** `scrollWidth > clientWidth + 1` 计为**被裁**。**阈值 0，不给容差** |
| **锚点必须落在「自己裁切」的盒子上，不是文本节点** | `overflow:hidden` **只拦它自己那一层**。文本外套一层 `<span>` 时，span 的宽度由内容决定 —— 它**永远不会超出自己**，`clientWidth` / `scrollWidth` 恒为 0 或恒相等，`scrollWidth > clientWidth + 1` **永远为假 → 恒绿**；真正溢出的是它的父盒。表格里就是 `th` |
| **锚点怎么找** | 从 `th` 起：`th` 自身 `overflow-x` 为 `hidden`/`clip` → 用它；否则**往上找最近的裁切祖先**。找不到任何裁切祖先 → **该列不进分母**（没有裁切发生，谈不上"被裁"），并计入 `未覆盖列数` 打出来 |
| **分母** | **表头文字 1~6 全角字的列**。**三类排除，每一类都要单独打出来**：① **空表头**（`rowSelection` / `radio` 槽位，0 字，没有文字可裁 → **必然为绿**）；② **表头 > 6 全角字**（归 T-03 + `ellipsisTitle`）；③ **找不到裁切盒**（没有 `overflow-x:hidden`/`clip` 的祖先，谈不上「被裁」）。输出固定三段式：`被裁 0/10 列@1234；另有 1 列表头 >6 全角字、2 列空表头、0 列无裁切盒，不入分母`（**按档位分列打印**，不许合并；数的来源以该页该档实测为准）。**为什么要分三类**：合成一个「另有 N 列不入分母」，看报告的人无法判断是判据放过了它们、还是它们根本不适用 —— 而**必然为绿的分母比没有分母更危险**，它会把 `0/10` 这种虚胖读数固化成「检查过了」 |
| **与 W-01 的分母是两套口径，不许统一** | T-04 量**表头标签**（短标签，字数就够）；W-01 量**列的值**（值才需要「可断性」）。硬把两条并成一个口径，必然误伤其中一条：按字数会让 `IQC-20261018-0342` 这类 token 列漏出 W-01 分母；按可断性会让 `不合格（潜在）事实陈述` 这类长表头混进 T-04 分母（它本来该归 T-03） |
| **为什么不是「折行」** | `white-space:nowrap` 只保证不折，不保证放得下。容器对 fixed 表的 `th`（原文 `.ant-table.fixed th,.ant-table.fixed td{white-space:nowrap;overflow:hidden;text-overflow:ellipsis}`）同时给了 `overflow:hidden; text-overflow:ellipsis`，于是放不下时的失败形态是**被裁掉并显示省略号**：`序号` 会显示成 `序…`。判据得跟着失败形态走 |
| **为什么 0 容忍** | 给 ±4 松量就是**放宽换绿**：`序号` 在 866 档只裁 4px（列宽 48 / 可用 24 / 文字自然宽 28），给 ±4 恰好把唯一的负例放过去，这条判据就变成恒绿 |
| **为什么分母按档位分列** | 同一列在 866 档裁、在 1026 档不裁（`序号` 48→57，可用 24→33）。合并成一个「1/16」会让这条判据的红绿取决于档位加权，而**档位不是产物属性** |
| **现成负例（不用另造）** | 把 `example-06` 的 `序号` 列宽改回 **48** → 866 档必红（`example-06` 的表头文本直挂 `th`，所以 `th` 就是裁切盒）。教材已改成 **54**（从 `任务单号` 挪 6，Σ 仍 866，留 2px 余量），所以现在的绿**理由是修了，不是判据看不见** |
| **>6 字的表头往哪去** | 不在本条分母内，但**必须配置 `ellipsisTitle`**（悬停可见全名）；没配的归 T-03 管 —— T-03 把渲染行数卡在 ≤2，长表头不许靠「多占几行」兜底。这是给长字段名留的**正当出口**：要求在数据里显式声明，而不是让判据看不见 |
| **正例** | `example-06`@1026：8 列全部 `scrollWidth ≤ clientWidth + 1` → `被裁 0/8 列@1026` PASS |
| **反例** | `example-06`@866（未修前）：`th 序号` 列宽 48 / 可用 24 / 文字 28 / 行盒 1 / **被裁 Y** → `被裁 1/8 列@866` FAIL |

**T-01 与 T-04 的锚点类型不同，这是两条判据的分水岭**：

| 判据 | 量什么 | 锚点为什么必须是它 |
|---|---|---|
| **T-01 / T-02 / T-03**（折行） | `Range.getClientRects()` 的 **`top` 去重个数** > 1 | 对 **inline 有效**（每个行盒一个 rect）—— 折行只发生在行内排版里，所以锚点必须是**文本节点/最内层 inline**。**必须按 `top` 去重**：ellipsis 的尾巴会多切一个同 `top` 的 rect，不去重会把「被裁」读成「折行」 |
| **T-04**（被裁） | `scrollWidth > clientWidth + 1` | 必须落在**有 layout box 且自己裁切**的元素上；对 **inline 恒为 0/0**。锚点必须是**裁切盒** |

> **这一行值得单独立出来，因为它是「用对了 API、选错了对象」** —— 比写错公式更难发现：代码里 `scrollWidth > clientWidth` 读起来完全正常，只是在 inline 上永远拿不到真值。同一份实现里两条判据的锚点类型相反，是**故意的**，不是不一致。

### 关于表头：为什么撤掉「折行」，却必须立「被裁」

上一轮曾经有一条判据叫「`th` 不得折行」，被删掉了，理由是**它结构上不可能为红**：

1. 容器对 `.ant-table th` 写了**无条件**的 `white-space:nowrap`（原文 `border-bottom:1px solid var(--ant-border-2);white-space:nowrap;font-size:14px}`）—— `th` 在结构上不会折行；
2. 两档实测：list 页 12 列、overdue 页 9 列，`th` 行盒 >1 的列数 **0/12、0/9**；
3. 当初判它折行的证据，是把 1920×1440 的缩放截图放大后读的**字粘连**。**截图能证明「观感差」，不能证明「某个元素折行」** —— 后者必须量 DOM。

**但「不折行」不等于「没问题」。** 我在撤折行时顺手把整族表头判据一起排除了，这一步是错的：`nowrap` 换来的不是「表头一定放得下」，而是「放不下时改成横向裁切」。所以：

| | 折行判据 | T-04 被裁 |
|---|---|---|
| 能不能找到让它红的输入 | **找不到**（`nowrap` 无条件，任何宽度都不折） | **找得到**（把 `序号` 改回 48 就红） |
| 结论 | 恒绿 → **撤** | 可判 → **立** |

**判「一条判据能不能立」的标准，是「能不能构造出让它红的输入」，不是「当前样本红不绿」。** 这两条不是同一件事：撤折行是因为它恒真，不是因为表头这一族都不该判。

## 3. 列宽预算

### W-00 布局锁定：`fixed` 与「每列 width」是**一对**，缺一即 FAIL

| 项 | 内容 |
|---|---|
| **判据** | ① `Table` 的 `tableLayout === 'fixed'`；② `columns[].width` 覆盖率 **100%**（每列都有）。**两条同时成立才 PASS**，任一不成立即 FAIL |
| **`width` 的两种写法等价** | `150` 与 `"150px"` 是同一声明，判据必须两种都解析。用 `float(w)` 直接读会把 `"150px"` 判成「未声明」—— 一份 11/11 全声明的产物会被报成 `0/11 = 0%` |
| **为什么必须成对** | 同一份 `example-06`，三种改法的对照实验：<br>① 去掉 `width` 且不用 `fixed` → 1600 档短字段 **40/40 全折行**、行高 79；1440 档表宽 892 > 内容宽 866（横向溢出）<br>② **保留 `width` 但布局是 `auto`** → 声明值只是**建议值**，浏览器按 min-content 继续压：`类型` 72→**62**、`事实陈述` 330→**238**<br>③ 只加 `fixed`、不写 `width` → 8 列各 108px、折行 0/40，代价是长列被裁 |
| **正例** | `tableLayout:'fixed'` + 11 列各带 width → 声明 = 渲染（再由 W-02 逐列校 ≤2） |
| **反例** | CAPA list 页：`width` **11/11 全有**、`tableLayout` 缺失 → auto 布局 → `类型` 72→62 → Tag 内宽 22 → `纠正` 竖排（T-01 红） |
| **为什么单独成条** | 「声明率 100%」是**必要条件，不是充分条件**。CAPA 恰好是"100% 声明率 + 大面积折行"的反例：只查声明率的判据会给你一个绿，而屏幕上是烂的 |
| **运行时载体** | 本条由 `P7` 承载（**不另立一条重复判据**），输出必须带红的理由：`P7 列宽生效: declared=11/11 (100%) fixed=false → FAIL(原因=fixed)`，理由枚举 `declared` / `fixed` / `both`。**不要拆成 P7a/P7b** —— `0/8 + fixed` 会读出"P7b 绿"的半绿，而「只 fixed 不写 width」不是解法（8 列各 108px、长列被裁） |
| **不许在渲染层自动补 `fixed`** | 「每列都有 `width` 就自动加 `fixed`」听着像兜底，实际是**在渲染时替产物把病治好**：CAPA 的 `类型` 会从 62 回到 72、折行 33/39 → 0/39、P7 两页由红转绿，**反样本当场失去判决力**（老刘量过：757 条断言不动，但反样本变绿）。判据的职责是看见病，不是替他吃药 —— 要修就改产物 |

### W-01 列宽下限（量实测，不量字数）

**先定分母（口径先后改过两次，务必看这一节）**

分母不是「短列」，是**「值必须整条放得下的列」**。判它的是**值里有没有可断点**，不是字数、更不是渲染行数：

| 进分母 | 不进分母 |
|---|---|
| **未声明出口**，且该列**最长值里没有可断点**（token）→ `needW` 的语义成立 | **声明了出口**的长文本列（`ellipsis:true` / `wrap` + `maxLines`）→ 归 T-02 / T-03 |
| 含 `Tag` / `Button` 的列（`needW = Σ控件外宽 + gap × (n−1)`） | **未声明出口、但值里有可断点**（正文类长文本）→ 归 T-02（「三者皆无且 ≥2 行」已经抓了，不必在 W-01 再红一次） |

**可断点判定（够用就行，不许再细化）**：① 含空格分隔词 ≥3 个（`待质检 已完成 复核中`）→ 可断；② **连续 CJK 字符 > 6**（`不合格（潜在）事实陈述`、`设备点检记录缺失`）→ 可断；③ 其余一律算**不可断**（`IQC-20261018-0342`、日期、单号、`序号`、`状态`、Tag 文本）→ 进分母。

**为什么是「可断性」，不是字数、也不是行数** —— 这两种错法老刘都撞过：

| 错口径 | 实例 | 后果 |
|---|---|---|
| 「整格 ≤ 6 全角字」 | `任务单号` 的值 `IQC-20261018-0342` 是 **19 个半角字**，却不可断 | 被当成长文本列 → **出分母** → 分母变 4，**漏掉一列真正需要宽度的** |
| 「渲染 ≤ 1 行」 | 行数由**被修的列宽**决定 | 列越窄 → 越容易折成 2 行 → 越像长文本 → 出分母 → **越坏的列越免检**（循环定义，最坏的一种） |

> **T-04 的分母是另一套口径，不许「统一」**：T-04 量**表头标签**（短标签，`表头 1~6 全角字` 就够），W-01 量**列的值**（值才需要可断性）。两条判据量的不是同一种文本，硬统一就会让其中一条误伤 —— 见 §T-04 分母行。

三条理由：
1. **消灭不可满足的数**：CAPA `事实陈述` 的 `needW` 算出来是 **532**，而整表只有 **866**。这类列出了分母，这个数就**不参与判定**（**但仍对全列打出来**，见下）；也就不需要「红但不归因」这种中间态；
2. **红才有正确的动作**：改完后 W-01 红只意味着「这列窄到放不下它本该放下的东西」，作者看报告会去加宽 —— 而不是被教去把表撑到 532；
3. **不留重复归因**：长文本列由 T-02 / T-03 一条管到底。


**为什么长文本列必须出分母**：`needW` 的语义是「这列最短要能放下**一整条不可断的内容**」，这句话只对**没有出口的短值列**成立。一旦这列声明了 `ellipsis` / `wrap+maxLines`，语义就变成「能放多少放多少，剩下的悬停看」，`needW` 不再适用 —— 拿 532 去要求一个配了省略号的列，等于要求它**把全文显示出来**，而这两件事互相取消。

```
needW(col) = ceil(实测文本宽) + 24 + (chip列 ? 16 : 0) + (sortable ? 20 : 0)

分母内列     ：实测文本宽 = max(表头文本宽, 该列最长值文本宽)   ← ellipsis 列已出分母，不在此列
type:'index' ：豁免表头项，needW = max(48, 行号最大位宽 + 24)
多控件列     ：needW = Σ(各控件外宽) + gap × (n−1)   ← 不是 max，也不是任意一个

24 = cell 左右 padding 12×2
16 = Tag 左右 padding 7×2 + 边框 1×2      ← 该列的值是 Tag / Button 时必须加
20 = 排序图标 16 + 间距 4

【硬约束】量文本宽用的字体，必须取「承载这段文本的最内层元素」自身的 computed
         font-family / font-size / font-weight；该元素自身的 padding 由它的
         computed padding 扣除，不许用父元素（td / th）的值代算。
         Tag 列 → 取 .ant-tag 的 12px；表头 → 取 th 内层文本的；正文 → 取 td 的。
```

**为什么这条要写成硬约束**：「用单元格字号代算」不是精度问题，是**判据不可判定**。同一份数据按 `td` 的 14px 去算，「状态」列 `needW = 84`；按 Tag 的 12px 算是 `78`；声明 80 —— 前者红、后者绿。**红绿取决于实现者选了哪个字号，而不是排版对不对**，那这条判据就没有判决权。实测已确认：`example-06` 的「状态」列渲染 80，按 Tag@12px 得 78（绿，与渲染一致）、按 td@14px 得 84（红）—— 差的正是那 4px，也正是选错口径会造成的误红。

**声明宽 `columns[].width` 必须 ≥ `needW`。判定由 `check_ui_shape` 的 W-01 执行（运行时量实测文本宽）；交付闸门在 `check_release.py`（I-09 第三阶段接线）。`validate_prd_json.py` 不做此项 —— 它读不到字体度量。** 输出必须带分母与**排除说明**：`低于下限 0/6 列（另有 2 列声明了 ellipsis、0 列无出口长文本，不入分母）` —— 与 T-04 的空表头同一条规矩：**被排除的数要打出来，否则「0/8」和「0/6」的差别没人看得见**。`needW / 声明 / 渲染` 三数**对所有列照打**（诊断信息不缩水，只是不计入分母）—— 不让步，否则下次有人会以为这两列没被量过。

**前置与归因**：`fixed` 不成立（W-00 红）时，W-01 判 **`FAIL(cause=prereq:W-00)`**，**写明是哪一条前置** —— 只写 `prereq` 等于没写原因。**不是 SKIP**（SKIP 会让存量产物在 needW 这一项上免检，与 P18 同款），且**三数照打**。`prereq` 只用于「W-00 不成立」，**不再用于长文本列**（长文本列已出分母，见上）。

**同一条红在两个用途下的处理不同，必须写清**：

| 用途 | 允许一条病红两次？ | 报法 |
|---|---|---|
| **回归基线**（`expected-fails` 集合相等） | **允许，宁可多一条** | 集合相等要稳：判据数量稳定、`cause` 稳定，比「红得漂亮」重要 |
| **缺陷计数**（报给人看） | **不允许** | P24 标成 **`(前置) 由 P7 引起`**，**不计入独立缺陷数**；独立缺陷数只按 `cause` 去重后计 |

这样就不必为了「重复计数」去动 SKIP 白名单 —— 那会把一个**报法问题**升级成**状态机问题**。
- 该列**没写宽 / 写了百分比宽** → 该列**不出结论**，计入 `未覆盖列数`；整表都不可判时打 `无法判定 n/n`（**不落 PASS** —— 不报分母的绿与静默绿同款）。
- 该列**有 px 声明宽且 `fixed` 成立** → 照判，红就写 `W-01 列宽不足: 状态 声明40 needW78 差38`。

**多控件列取「和 + gap」，不取 max。** `操作` 列两个按钮：详情 44 + 开始 30 + gap 6 = **80**；取 max 只有 52 → 低估 28px，而 28px 正好是「第二个按钮被挤到下一行」的宽度。这条是 W-01 唯一会低估的形态，写在这里而不是藏在实现里。

**分母改口径之后留了一个空档：见 `backlog.json` 的 XX-043**：一个**配了 `ellipsis` 的列被压到 40px，谁都不红** —— T-02 因为「有出口」而绿、T-03 因为值短而不红。补丁不是把它塞回 `needW`，而是一条显式下限 **`声明宽 ≥ 表头文本宽 + 40`**（文本宽**不含** padding，40 = cell padding 24 + 省略号 16；**不许写成 `表头 needW + 40`**，那会把 padding 算两次）。见 `backlog.json` **XX-043**。

**作者预算用的估算算式**（不参与判定，误差 ±8%）：

```
est ≈ (max(表头字数, 最长值字数) 加权) + 24 + (chip列 ? 16 : 0) + (sortable ? 20 : 0)
全角字 14px / 半角字 7.8px（14px + tabular-nums ≈ 0.557em）
```

| 项 | 内容 |
|---|---|
| **为什么算式不参与判定** | 字宽受字体族、字重、`letter-spacing`、标点压缩影响。`取样·样品` 里的 `·` 实测约 7px，算式按 14px 算 → 算式会把一个本来放得下的列判成不合格。**用算式当判据，红绿取决于估算准不准，而不是排版对不对** |
| **正例** | 「纠正纳期」：表头 `纠正纳期` 实测 56，最长值 `2026-10-26` 实测 78 → `needW = 78 + 24 + 20(可排序) = 122`；声明 124 → PASS |
| **反例** | 假设把表头「责任部门」改成「责任部门/归属单位」（9 全角字 ≈ 126）→ `needW = 126 + 24 = 150`，而列宽仍按旧值 120 → FAIL。**注意：门限是"最长的那一项"，不是平均值** —— 表头比值长时，加宽值救不了它 |
| **Tag 列的字号必须取 Tag 自己的** | `Tag` 默认字号 12px，而单元格是 14px。同一串「不合格」在 Tag 内比在 `td` 里窄约 1/7。**用单元格字号去量 Tag 文本会把本来放得下的列判红**（反之则漏判）。实测时取承载文本的最内层元素的 computed `font-size` / `font-weight`，不是父 `td` 的。CAPA 的 `类型` 声明 72 就是按「最长值 42 + cell 24 = 66，留 6 余量」算的 —— 漏掉的是 **Tag 自己的 16px**（左右 padding 7 + 边框 1） |
| **`index` 为什么豁免表头** | 「序号」是槽位标签，不是需要被扫读的字段名；它参与表头测量会把 48 抬到 52，而 52 会让 8 列的总下限无谓地多出 4px。这是**有意的例外**，写在条款里而不是藏在代码里 |

### W-02 声明必须等于渲染

| 项 | 内容 |
|---|---|
| **判据（主）** | 令 `k = table.clientWidth ÷ Σ声明`，逐列 `abs(渲染宽 − 声明宽 × k) ≤ 2`。**任一列超差即 FAIL**。**条文语义 =「每列是否按同一个比例缩放」**，不是「允许偏差 ≤2」—— 阈值只是这个语义的量化，`k` 必须打进报告 |
| **为什么要乘 `k`** | `fixed` + `width:100%` 下浏览器把「表宽 − Σ声明」**按同一个比例**摊给各列。`example-06`@1026：Σ 866 → 表宽 1026，`k = 1.18476`，8 列被同比例放大（54→64、182→216、80→95）；残差 `0.02 / 0.37 / 0.10 / 0.03 / 0.26 / 0.03 / 0.22 / 0.26`，**最大 0.37，对阈值 2 有 5 倍余量** —— 均匀缩放本来就该残差近 0。按原式 `abs(渲染 − 声明) ≤ 2` 则 8 列全红、**把教材判死** |
| **`k` 的适用边界（不满足就退回 `k = 1`）** | 只有「**每列都是 px 声明宽**」时 `k` 才有意义。缺任一列宽、或混了百分比宽时，表宽要在「无宽列」和「有宽列」之间二次分配，那个比例**不是 `k`**，换算出来的差是假的 → 此时 `k = 1`，退回 `abs(渲染 − 声明) ≤ 2`。这种情况本身已经让 W-00 红（声明率不是 100%），W-02 不必重复报同一件事 |
| **W-02 里不许顺手判 Σ 闭合** | `k` 由 `表宽 ÷ Σ声明` 推出，所以 **`Σ(声明 × k) ≡ 表宽` 恒成立** —— 在 W-02 里判 Σ 是拿定义当判据，永远为绿（与 P17 的 `Σ col.offsetWidth ≡ 表宽` 是同一个陷阱）。Σ 是否合理归 W-00 / Σ 那一侧，**W-02 只回答「每列缩放是否一致」** |
| **`k` 的合法性不由 W-02 承担** | 8 列全声明成 `100`、Σ=800 与表宽 1026 的差，`k = 1.2825`，W-02 照样能 PASS —— 因为**每列确实按同一比例缩放了**。那是「声明总预算不对」，归 Σ 判据；把两件事混进一条判据，会让 W-02 既判缩放又判预算，红绿说不清 |
| **为什么 Σ 不能当主判据** | `table-layout:fixed` + `width:100%` 下，浏览器会把差值**等比摊给各列**，于是 `Σ渲染 ≡ 表宽` 恒成立。I-07 §3.8 的头号缺陷（`width:48` 漏单位 → 8 列全 108.25px）就是靠这条漏过去的：JSON 里 Σ 看着闭合，屏幕上每列都是 `表宽 ÷ 8` |
| **正例** | @866（`k = 1.000`，**与原式逐字节等价 —— 这是「没放宽」的证据，必须写出来**）逐列差 ≤1；@1026（`k = 1.18476`）：`54×k = 64.0`/实测 64、`182×k = 215.7`/实测 216、`125×k = 148.1`/实测 148、`146×k = 173.0`/实测 173、`88×k = 104.3`/实测 104、`103×k = 122.1`/实测 122、`80×k = 94.8`/实测 95、`88×k = 104.3`/实测 104 → 最大残差 0.37，8 列全 PASS |
| **反例** | ① 声明 `width: 48`（无单位，CSS 判非法并忽略）→ 8 列等宽 108.25 → 逐列差 60+ → FAIL；同时 `Σ` 仍显示与表宽相等 → **只有逐列判据能抓**。② CAPA 两页（`auto` 布局）→ 渲染与声明**不成比例**：`类型` 72→62、`事实陈述` 330→238，同一张表里有的被压有的没压，`k` 算出来也没有一个值能对上 → 逐列差 10 / 92 → FAIL（与 W-00 的 `fixed=false` 是**两件事**，见 W-01 的前置说明） |

### W-03 四条不变量（写完必须同时成立）

1. `tableLayout === 'fixed'`（W-00 前半）；
2. 每列都有显式 `width`，声明率 **100%**（W-00 后半）；
3. 每列 `width ≥ max(48, needW)`（W-01）；
4. 逐列 `abs(渲染 − 声明 × k) ≤ 2`（W-02）。

**顺序是报告顺序，也是归因顺序。** 三条依赖关系要分开说：

- **1 / 2 不成立 → 第 4 条（W-02）不出结论**：`fixed` 缺失时渲染本来就不等于声明，判了也不作数（CAPA 的 `330→238` 就是这么出来的）；
- **第 3 条（W-01）照判，但归因为 `cause=prereq:W-00`**（写明是哪一条前置），不许归成「列宽不足」—— 那时差是 auto 布局的产物；**也不许 SKIP**（SKIP 就是免检）；
- **第 2 条不成立时，无宽列在第 3 条里记 `未覆盖列数`，不出结论、也不落 PASS**。

所以「一条病红两次」只发生在 **W-00 与 W-01 / W-02** 同一份报告里，处理方式是用 `cause` 区分（`prereq:W-00` / `needW` / `layout`），**不是让某一条闭嘴** —— 让判据闭嘴就是给下一份产物留免检口子。

## 4. 字号与行高

### S-01 字号档 ⊆ {18, 14, 12}

| 项 | 内容 |
|---|---|
| **判据** | 遍历产品态内容区所有可见元素的 `getComputedStyle().fontSize`，去重成**集合**（±0.5 内视为同档），判 **`集合 ⊆ {18, 14, 12}`**。**档数只作读数打印，不参与判定** |
| **为什么删掉「≤ 3 档」** | `⊆ {18,14,12}` 的大小上界就是 3 —— 「≤ 3 档」在任何输入下都随之成立，是**恒真的一半**（与 `①+③≡clientWidth`、`Σ(声明×k)≡表宽`、`nav > nav` 同族）。子集关系推出档数上界，两条**不是独立约束**；并列写成「≤3 档 且 ⊆」会让人以为档数被单独查过一次 |
| **三档的用途** | 18 = 页面标题（`h1`，字重 ≥600）；14 = 正文与表格；12 = 辅助信息（分页、提示、单位） |
| **正例** | `{12, 14, 18}` → PASS（读数：3 档） |
| **反例** | ① **仓库内实例** `example-05`：字号集合 `{12, 13, 14}` —— **只有 3 档、`P19`（≤3 档）判绿，`S-01` 仍红**，因为 13 不在集合里。这就是「**档数判据放过 3 档全错**」的现成证明，不必再构造；② 历史证据 §3.2 `P19`：`{12, 13, 14, 24}` → FAIL —— **理由是 13 与 24 不在集合内**，不是「超过 3 档」（后者只是同一次失败的另一面，读数 4 档）。24px 是某个标题，13px 是分页与 `select` 图标 |
| **为什么禁 13** | 12 / 13 / 14 三档相邻只差 1px，视觉上分不出，却让"这一处该用哪个"永远有争议。这是 I-07 §3.1 已经裁过的：**档位密度本身就是债** |

### S-02 行高

| 项 | 内容 |
|---|---|
| **分母** | **行内文本行盒数 == 1 的数据行**（`tr`，排除 `<thead>` 表头）。`分母 == 0` → `SKIP(无单行数据行)` —— **条件式 SKIP，值里必须带条件，不许裸 `SKIP`** |
| **判据** | ① 上述行的 `tr.getBoundingClientRect().height ≤ 34`；② **正文**的 `lineHeight ÷ fontSize ∈ [1.40, 1.60]` |
| **「行盒数」怎么数** | 与 `T-01` **同一量法**：`getClientRects()` 按 `top` 四舍五入去重，得数 > 1 即多行。**两处必须同口径** —— 否则同一格会在 T-01 算两行、在 S-02 算一行，两个判据对同一次改动给出互斥结论 |
| **为什么不是「所有 `tr` ≤ 34」** | `T-02` 允许 `wrap + maxLines:2`，而**两行单元格的行高必然 > 34**（14 × 1.57 × 2 + padding ≈ 58）。CAPA 的 `58 / 68 / 78` 就是**合规的两行 / 三行**，按「所有 `tr`」判会把合规产物判红。分母换成单行行之后，原条文想抓的仍然抓得住（AntD `size=middle` 行高 48，见上方冲突条；`example-05` 的 `{39:6}` 单行 39 仍红） |
| **正文比的分母** | **排除** `button` / `.ant-btn`（控件 `line-height:1` 是规范值，不是正文）；**标题**（`h1`–`h6` / `.typography` 标题）**单列统计，不进正文分母**。实测三份产物正文比**全是 1.57**，`1` 只出现在 `.ant-btn`、`1.44` 只出现在 `h1` —— 不写这句，接线后 `example-06` 会被算 6 个违规、CAPA 4 个、`example-05` 3 个，**全是按钮**（分母与它想判的对象不一致，与 P24 同型） |
| **32 与 34 的关系** | 32 是**设计值**（`padding 5+5` + `line-height 21`），34 是**实测值**（`tr` 多 2px 行内盒余量）。**阈值写 34**，不是 `== 32` —— 写 32 会逼人去删边框或改 padding，那是改实现迁就判据 |
| **正例** | 单行 `tr` 34 → PASS；正文 14/22（比 1.571）→ PASS |
| **反例** | 单行 `tr` **39**（`example-05` 的 `{39:6}`）→ FAIL，**登记红保住**。撑到 58 / 68 / 78 的**多行**行不进分母，不判 —— 它们不是「行高错」，是「这一格本来就该占两行」 |
| **与 `P9` 的分工（归属唯一化）** | **「行高上限 ≤34」只归 `S-02①`**（代码 id `S-02a`）；`P9` **只保留「跨 `tr` 一致性（极差 ≤2）」**，删掉 `mx <= ROW_MAX_H` 那半边（旧实现带 `mx <= ROW_MAX_H`；上限归 `S-02a`，`P9` 只判组内极差）。否则同一次超标会被两条判据各报一次，读报告的人无法判断该改哪一条。`P9` 的极差还必须**按行盒数分组**比（单行行比单行行、两行行比两行行）—— 否则一个合规的两行格（`T-02` 允许）夹在一堆单行里，极差必然 >2，那是**必然事件**、不是缺陷。`CAPA` 的 `58/68/78` 正好同时踩了这两件不同的事，这就是「行高看起来不可判」的来源：不是不可判，是**上限与一致性被写进了同一条判据**。**搬家的方向记在这里：`S-02a` 的上限继承自 `P9`，`P9` 因此只剩极差**（它的组内极差与两条条件式 SKIP 见下方 `P9 行高一致性` 条） |
| **登记红搬家（`example-05`）** | **裁后**：`P9@1440/1600` 由 `FAIL` 变 `PASS`（`{39:6}` 是单值，`spread = 0`），`S-02a@1440/1600` 由「未接线」变 `FAIL`（单行 39 > 34）。**一出一进、总数不变** —— `EXPECTED_FAIL` 重登时按「**搬家，不是放宽**」记，并逐条写明哪条去了、哪条来了。`CAPA` 的 `P9` 红**不能**当「单行行高」的证据：它的 58/68/78 是多行撑高，分工后那部分只由 `P9` 的分组极差判 —— 但**分组后若 58 与 78 落进不同行盒组、且每组 n=1，就没有可比基数，`P9` 只能报条件式 SKIP**；结论**以实测为准**，不许为了保住这个红去并组。**未裁**：`EXPECTED_FAIL` 保持 22 条，`P9` 与 `S-02a` 在 `example-05` 上**双红同因**（单行 39 > 34），已在 `expected-fails.json` 的 `watch_out` 与 `CHANGELOG` 注明 —— **不许读成两个缺陷**，也不许为了去重去动阈值或摘名单 |

### S-03 字重

| 项 | 内容 |
|---|---|
| **判据** | 产品态出现的 `font-weight` 去重成**集合**，判 **`集合 ⊆ {400, 500, 600}`**（个数只作读数 —— 集合只有 3 个元素，「≤ 3 个」由子集关系保证，写上去就是恒真的一半） |
| **用途** | 400 正文 / 500 强调（表头、关键字段）/ 600 页面标题。**不出现 700 及以上的正文加粗**（中文 700 在 14px 下会糊成一团） |
| **反例** | 同一页里出现 400/500/600/700 → FAIL |

### P9 行高一致性（阈值列：`极差≤2`）

> `P9` 不是本文件的 S 组条款，但它是「行高」这件事的另一个判据，**与 `S-02a` 同域**，所以阈值与分母必须在这里写清楚，否则又要靠读代码才知道它在判什么。

| 项 | 内容 |
|---|---|
| **阈值列** | **`极差≤2`**（三个分支 —— 判红/判绿/条件式 SKIP —— 的阈值列统一写这一句，不许再出现 `且 ≤34`） |
| **上限归属与记账结果** | `P9` 只判**组内**极差 ≤2；「单行行 ≤34」的上限归 `S-02a`，`P9` 不判上限。`example-05` 的 `{39:6}` 在新口径下是**单值**、`spread = 0` → `P9` PASS，`S-02a` 接手 FAIL —— **一出一进**，`EXPECTED_FAIL` 22 → 20（**搬家，不是放宽**）。**若 `P9` 仍带上限**，两条会在同一缺陷上双红（`watch_out` 记「双红同因」）—— 那是同一件事被记两次，**不许读成两个病**，也不许为了去重去动阈值或摘名单 |
| **判据** | 对表格数据行**按「行内文本行盒数」分组**（单行行一组、两行行一组、三行行一组……），**只在组内**比 `tr` 高度极差，每组都要 ≤2 |
| **上限归属** | **`≤34` 不归 `P9`，归 `S-02a`** —— 一个阈值只能有一个判据拥有。`P9` 越权带上限，同一次超标会被两条各报一次，读报告的人不知道该改哪条（与 `S-02①`/`T-02` 的分工同型，同一分工的第二次落地） |
| **跨组不可比** | 「单行 34」与「两行 58」是两种**合规形态**，互相不能比。旧判据拿全部行算极差，2 行数据（单行 1 + 多行 1）会得 `58 − 34 = 24 → FAIL` —— 那是**跨组误判**，不是缺陷 |
| **条件式 SKIP（两条）** | ① `SKIP(有效数据行 0 < 2，无表格数据行)`；② `SKIP(无任一行盒组 ≥2 行：单行 %d / 多行 %d / 行盒 0 的 %d 行量不到)` —— ② 是分组后新长出来的状态：**本来就没有可比基数**，与「有基数且算出来了」必须分开。两条都把**条件与实测值写在 `value` 的 `SKIP(…)` 里**，`skip_allowed()` 按 id + 前缀放行 |
| **「未判组」必须显式打出来** | 分组后哪些组因计数 <2 而未判，要写进输出（`②` 那行的 `单行 / 多行 / 行盒 0` 三个数就是），**不许折进 PASS 行** —— 把「没比」写成「比过了」是静默绿，与 `CONTENT_ZERO` 那类同族 |

## 5. 留白与层级

### L-01 4px 栅格

| 项 | 内容 |
|---|---|
| **判据** | 区块级元素（`.ant-content` 的直接子元素、其容器 `gap`、卡片内 `padding`）的 `margin` / `padding` / `gap` 取值必须 ⊆ `{0, 4, 8, 12, 16, 24, 32, 40, 48}` |
| **量法** | 枚举这些属性，按像素取整后比对集合；**不做除法**（10 能被 2 整除但不是栅格值） |
| **正例** | 区块 `gap:16`、卡片 `padding:24`、表单项 `margin-bottom:12` → 全部在集合内 PASS |
| **反例** | 区块 `gap:18`、卡片 `padding:20`、表单项 `margin-bottom:10` → 3 处 FAIL |
| **区块间距的定值** | 同屏相邻区块间距取 **16**（密集）或 **24**（分组）；同一页只用一种，混用视为不一致 |

### L-02 层级：卡片用边框，浮层用投影

| 对象 | 判据 | 正例 | 反例 |
|---|---|---|---|
| **卡片**（`Card`） | `boxShadow === 'none'` **且** `borderWidth ≥ 1px` | `border:1px solid #f0f0f0; box-shadow:none` | `border:none; box-shadow:0 1px 6px`（阴影在密集排布下互相叠加，形成第三层噪音） |
| **浮层**（`Modal` / `Drawer` / `Dropdown` / `Tooltip`） | `boxShadow !== 'none'` | `box-shadow: 0 6px 16px rgba(0,0,0,.08)` | 浮层无投影（与背景粘在一起，分不出层级） |

**为什么定案为 border 而不是"二选一"**：一条"二选一"的规范等于没有规范 —— 两个产物按相反方向做都能自称合规，评审时无法判定。选 border 的三条可复算理由：① 密集排布下投影会叠加成第三层视觉噪音；② 投影在 `overflow:hidden` 的滚动容器里会被裁掉，border 不会；③ border 宽度能被 `getComputedStyle` 精确读到，投影的视觉强度不能。

### L-03 圆角三档

| 档 | 值 | 用在哪 |
|---|---|---|
| 小 | `2px` | 标签、`Tag`、徽标 |
| 中 | `6px` | 按钮、输入框、选择器 |
| 大 | `8px` | 卡片、弹窗、抽屉、下拉面板 |

出现第四档 → **WARN**（不是 FAIL）：圆角不影响可读性与密度，只影响一致性。

### L-04 容器层数 ≤ 2

| 项 | 内容 |
|---|---|
| **判据** | 从 `.ant-content` 到任意文本节点，**带边框或投影的容器**层数 ≤ 2（卡片算 1 层，浮层不算因为它是另一个栈） |
| **正例** | `content` → 卡片 → 表格（表格无外框）→ 文本 = 2 层 |
| **反例** | `content` → 卡片 → 卡片 → 表格外框 → 文本 = 3 层（P5 三层噪音） |

## 6. 色彩

### C-01 有彩度颜色 ≤ 6 种

| 项 | 内容 |
|---|---|
| **判据** | 遍历内容区所有元素的 `color` / `backgroundColor` / `borderColor`，转 `rgb()` 后计算 `max(r,g,b) − min(r,g,b)`；**差值 ≤ 12 判为灰阶并剔除**；`alpha < 0.1` 剔除；去重计数 **≤ 6** |
| **6 个名额怎么分** | `primary` / `success` / `warning` / `error` / 1 个中性强调色 / 1 个品牌或语义保留位 |
| **正例** | `#1677ff` + `#52c41a` + `#faad14` + `#ff4d4f` + `#722ed1` = 5 种 → PASS |
| **反例** | 同一页里 `Tag` 用了 blue/green/red/orange/purple/cyan 六色 + 主色 + 链接色 = 8 种 → FAIL |
| **为什么剔除灰阶** | 灰阶是层级工具（文字三级、边框两级、底色两级），不是"颜色"。把灰阶计入会让任何页面都超限，判据立刻失效 |

### C-02 状态色全站唯一映射

| 状态 | 色 | 不许 |
|---|---|---|
| 进行中 / 处理中 | `processing`（蓝） | 用绿表示"进行中" |
| 成功 / 已完成 | `success`（绿） | — |
| 警告 / 待处理超期 | `warning`（橙） | 用红表示"待处理"（红=失败，语义冲突） |
| 失败 / 已驳回 / 已作废 | `error`（红） | — |
| 中性 / 默认值 | `default`（灰） | 给"否""无""未设置"这类默认值上色 |

**判据**：同一状态词在全站所有页面里的 `Tag.color` 必须相同。判定由 `check_ui_shape` 的 C 组执行（渲染后读 Tag 的实际背景色，跨页比同一状态词）—— **当前无自动判据**（C 组尚未实现，`validate_prd_json.py` 也不做：它读不到渲染色），接线登记在 **XX-044**。接线前这条由 §9 自检人工核，**不落 PASS**（不接线又落绿 = 静默绿）。

### C-03 涨红跌绿（中国市场惯例）

涉及涨跌 / 收益 / 增减的数据：**涨用红（`--ant-error`）、跌用绿（`--ant-success`）**。

**这是写作约定，不是判据** —— 判它得先知道「这个数相对什么在涨」，机器读不到语义；硬判会把 `跌幅 −3%`（数值下降、文字已说明方向）判反。所以它**不给 `PASS` / `FAIL`**，由评审人工看，也不登记接线（一条判不出红绿的条款不许占判据编号）。

## 8. 「不逊于直接用大模型生成的页面」= 六项对照

> Owner 的原话是"整体观感不应逊于直接用大模型生成的页面"。
> 这句话不能当口号：它是一个**比较关系**，所以必须写出"和谁比、比什么、怎么算赢"。
> 下表左边是基线（大模型直出的常见形态），右边是要求。**六项全部满足才算"不逊于"** —— 不做加权总分。

| 对照项 | 直出常见形态（基线） | 要求 | 量法 |
|---|---|---|---|
| **Q1** 首屏信息密度 | 5–8 行 / 6 列 | **整行 ≥14 / 列 ≥8** | 产品态首屏可见整行数、列数 |
| **Q2** 字号档 | 4–6 档 | **去重集合 ⊆ {18,14,12}**（见 S-01；档数只作读数） | 去重集合 |
| **Q3** 折行 | 普遍折行 | **短字段 0/分母、长文本全部显式三选一**（见 T-01/T-02） | Range 行数 |
| **Q4** 列宽 | 从不声明（0%），或声明了但布局是 `auto` | **`fixed` + 声明率 100% + 逐列偏差 ≤2**（见 W-00/W-02） | 逐列 |
| **Q5** 色彩种类 | 8–12 种 | **≤6**（见 C-01；**C-01 当前 `人工`**，未接线） | DOM 计算去重 |
| **Q6** 对齐 | 左右混排、图标错位 | **同列起始边极差 ≤1、区块左边界极差 ≤1**（见 A-01/A-03；**这两条与 C-02 均未接线（XX-044），现在只能人工核**） | Range 矩形 |

> **Q4 的基线必须写两种形态**：直出的常见做法是根本不写 `width`；但「写了 `width`、没写 `fixed`」在屏幕上与前者几乎一样烂 —— CAPA 就是这一种（11/11 全声明、auto 布局、列被压到 62）。只把基线定成"0% 声明"，会得出"我们已经 100% 了，所以这一项赢了"的错误结论。

### 为什么是这六项

它们覆盖的是"粗糙"在 B2B 界面里的**可测量成因**：挤（Q1）、乱（Q2/Q5）、折（Q3）、没排版（Q4/Q6）。六项都优于基线，等于这四类成因被逐项消除。

> **注意这句话的性质**：它是**论断**，不是判据。判据是上表六行。写在这里是为了让评审时能一句话说清"为什么是这六项"，而不是为了让谁拿它当检查项。

### 不做加权总分的理由

Owner 说的是"不逊于"，是**逐项关系**，不是总分。打分制会允许"密度高但色彩乱"互相抵消 —— 而那正是要治的病（CAPA 的密度不低、列宽也全声明了，但布局没锁定、4 档字号、短字段 33/39 折行；一旦允许平均，它会在"列宽声明率"这一项上拿到满分，把其余五项抵掉）。

### 与前六节的重复怎么处理

Q1–Q6 里 Q2/Q3/Q4/Q5/Q6 直接复用 V/T/W/C/A 的实测值，**不重复计分**。**但 Q5/Q6 现在引用的是尚未接线的条目**（C-01 未实现、A-01/A-03 在 XX-044）：引用一个不存在的判据比不引用更容易骗过读者 —— 它看起来像「既有体系的一部分」。所以 Q5/Q6 在接线前**只能记「人工核」**，不许记 PASS；Q1 复用 `P2a` 的实测值，只新增"可见列 ≥8"半边。Q 组的唯一新增价值是**把它显式挂在"和直出比"这个语义下**，让评审时有一张一句话说得清的对照表。

## 10. 本文件的维护

- **加条款**：必须同时给出「怎么量 / 阈值 / 正例 / 反例 / 什么输入让它红 / **谁判的**」。给不出「什么输入让它红」的条款一律不收 —— 那是本项目已经付过三次学费的坑（恒绿、判错对象、不生效）**；给不出「谁判的」的条款也不收——写了 `ERROR` 却没有任何校验器实现，比不给阈值更坏（详见速查表上方那条执行者说明）。
- **出现「永远满足 / 永远不满足」的读数时，先查分母，不许为它设计报法**：`needW=532 > 表宽 866` 这种数在说「它不该被算出来」，正确动作是把这类列移出分母（归另一条判据），而不是在 `cause` 里造一个「红但不归因」的中间态。同理，`①+③ ≡ clientWidth`、**`①+②+③ ≡ 父.offsetWidth − b`**（V-01 的闭合差就是这样：它从来只反映父节点，对内容被压窄免疫）、`Σ(声明×k) ≡ 表宽`、`nowrap` 下的表头折行，都属于「定义上恒真」—— 恒真/恒假的判据比没有判据更危险，它会把「查过了」固化下来。**恒假那一类更隐蔽**：`NAV_OUT_OF_RANGE` 曾把上界写成 `父宽 − content.offsetWidth`（**那就是导航宽本身**），代入化简是 `nav > nav` —— **恒真家族至少有读数，这条连读数都没有**，它只会一直显示 PASS。机械检查与处置见下一条。
- **降级/删除一条判据，要把「唯一单独触发的输入」写下来**：`N-e` 从判据降为诊断，理由是**它唯一的独立触发是「两档 padding 不同」（响应式留白，正当设计）** —— 一条只在合法产物上红的判据会教人加容差。记一笔，是为了下一个想「恢复 N-e」的人先看见这个输入；否则他会重新发现「它好像能抓常数宽」，再走一遍同一条弯路。
- **写区间 / 范围判据前，先把上界代入定义化简一次**：`x ≤ f(定义)` 化简后若出现 **`x ≤ x`（恒真）或 `x > x`（恒假）**，这条判据从来没判过东西 —— 而**恒假的那一种会一直显示 PASS，因为它根本不触发**（`NAV_OUT_OF_RANGE` 原来写 `0 ≤ 导航宽 ≤ 父宽 − content.offsetWidth`，右边正是导航宽自己的定义 → `导航宽 > 导航宽` 永假）。这是恒真家族的另一面：**恒真让人以为查过了，恒假让人以为查过了而且通过了**。动作相同 —— **删掉那半边，只留能触发的半边**（`NAV_OUT_OF_RANGE` 只剩 `导航宽 < 0`）。
- **写「结论行应为什么」之前，先读那一行是怎么算出来的**：`check_ui_shape` 的结论行是 `RESULT PASS if 红数 == 0 else FAIL`，而 `example-05` 在 `EXPECTED_FAIL` 里登记了 20 条 —— 要求「全量模式 PASS」是**结构上不可能**的验收（我把它写进过 XX-046，见需求单勘误 33）。同一行还有第二种错读：有登记红的样本**不可能是 `PASS`**（正常是 `FAIL`，有 `INCOMPLETE` 时是 `INCOMPLETE`），所以**结论行的颜色从来不是达标信号**，达标信号是「**V8 的 FAIL 集逐条相等 + 无 `INCOMPLETE` + 无 `SKIP-OUT-OF-WHITELIST`**」。不写明，下一个人的动作必然是把全量模式改到 PASS —— 结构上做不到，最后只剩 `continue-on-error`。与上一条同源：**不代入就写出来的阈值和验收，一半恒真、一半不可能**。
- **「计数 ≤ N」与「取值 ⊆ 某集合」并列写时，前半句恒真**：集合大小已经给出计数上界，那条计数就不可能单独红 —— `S-01` 原写「≤ 3 档 **且** ⊆ {18,14,12}」、`S-03` 原写「≤ 3 个 **且** ⊆ {400,500,600}」，两处的「≤3」都是子集关系的推论，**不是第二条约束**。处置：删掉计数那半边、降为读数；若要保留，必须换成一个集合管不到的**独立量**。**这一族在并列的 AND 句里最难发现** —— 单看每一半都像判据，合起来只有一个在判（立项时全文件扫过：`L-01` 只有集合、`C-01` 只有计数，均无并列；命中的只有 `S-01` 与 `S-03`）。
- **历史记录不改写，只在新引述处用新口径**：`CHANGELOG` 里已发生的条目、往轮实测记录里的旧判据名与旧阈值，**保持原样** —— 改写历史会让「当时为什么判红」失去可追溯性（`CHANGELOG:387` 的「页内字号 ≤3 档」就属于这一类：它记录的是那一轮做了什么，不是今天该怎么判）。新引述一律用当轮口径，并说明差异来源。**这与「证据文件里的实测数不改」是同一条**：证据记录事实，规范记录当下该怎么判，两者混在一起之后谁都不能信。
- **「没有 X」不是错，错的是拿它当结论而不是当要求**：这族句式（`没有…` / `绝不` / `恒不` / `不存在…` / `永远不会`）里，同一个词既可能是**禁令**，也可能是**对某个合法输入的描述**，还可能是**待验的检查项**。**词只能用来找候选，不能用来下结论** —— 命中数取决于词表：换一张词表，同一份文件的命中行就会变（候选集本来就由词表定义），所以判定不能停在计数上，必须逐条分类。扫到候选后逐条问三句，任一为「是」就留：① **它要求行为吗？**（不许 / 绝不 / 一律写…）→ 禁令，留；② **它描述的是某个具体输入的合法 / 已知形态吗？**（「内容区没有任何纵向重叠的兄弟时」「从不声明」）→ 形态描述，留；③ **它是待验的断言吗？**（checklist 上的「不存在 `max-width`」）→ 检查项，留。**三句都否**，才是要改的那一种：**它在描述整个文件的现状，而文件里就有反例** —— 例：原「没有 SKIP 分支」与同一张表第 11 行的 `SKIP(无单行数据行)` 只隔五行，处置是把断言改禁令（「没有豁免式 SKIP」）。**只有反例的规则，下次会被当成只适用于那一个反例，所以正样本必须一起写下来**：该规则立项时的候选里，`:30` 禁令 / `:44` 描述历史缺陷 / `:106` 禁令 / `:120` 描述合法输入 / `:268` DOM 事实结论 / `:600` 描述坏形态 / `:618` 描述尚未接线 / `:633` checklist 待验 / `:689`、`:696`、`:698` 描述缺陷与验收条件 —— **假断言 0 条**。
- **写进规范的数，必须由脚本现算，并连命令 / 正则一起记**：数离了命令不可复现，明年没人能复核。同一条命令换个工具量同一件事也会差 —— `wc -l` 与 `len(read().split('\n'))` 对同一个文件可以差 1（末尾无换行时多一个空元素）。**「口头给的数」接收方默认复算一遍，包括上级给的**：出现过一次「同一份输出，报出的数与实际行数不一致」，而当时我把两个数都当成了证据去论证「数会变」。**数不一致时的第一动作是追溯哪个错了，不是拿它当论据** —— 一个真、一个是算错的，那叫错，不叫不一致。**行号也会随编辑漂移**（同一处在两次报告里可以差 1–3 行），所以审计记录要引**原文短语**或正则，行号只能当索引用。**引原文时，那句原文必须是「删掉它就会有人来问」的那种** —— 引一段随时会变的代码，等于引一个即将失效的行号，只是失效得更安静（实例：`S-02` 分工行原引的那个行号，实际指向 `P7` 的 note 拼接；而它想引的 `mx <= ROW_MAX_H` 正是本轮要删的那句 —— 改完之后**既搜不到行也搜不到句**。已改引原文并注明「旧实现」）。
- **规范里不写进度**：出现「本轮 / 当前 / 尚未 / 已」时，那句话属于 `CHANGELOG`，不属于规范 —— 除非它指向一个**恒定时点**（「v6 定稿时」这类一次性历史锚点）。替换形态是「**目标 + 记账结果**」：`P9` 只判组内极差、上限归 `S-02a`；`example-05` 的 `{39:6}` 单值 → `spread = 0`，`P9` PASS、`S-02a` 接手 FAIL，`EXPECTED_FAIL` 22 → 20 —— **这段话不含时态，明年读仍成立**。实例：同一处先写「本轮已删」（假，因为没删），改成「本轮冻结、尚未删」（真，但一小时内过期）；**两次都是把进度写进规范**，只是错得一个显眼一个隐蔽。「什么时候删、在哪个 commit」是 `CHANGELOG` 的活，规范只留指针。
- **用于计数的正则，先在已知样本上验一遍**：找一个**必定返回 2** 的样本，读出 1 就是模式错了。实例：`@1[46]00` 能匹配 `@1600`、匹配不到 `@1440`（`@1`+`4`+`40` 对不上 `00`），整张表少数一半且**不报错**。**读数少一半的判据，和永远绿的判据一样危险**，区别只在它偶尔会对 —— 与「判据要在结构上可能为红」同族。
- **改阈值**：只能**收紧**。放宽必须写「冲突说明 + 让步理由 + 谁裁定」，并进 `CHANGELOG` 的 breaking 段。
- **删条款**：先证明它已被另一条完全覆盖，且删掉后没有任何产物变绿。删掉一个判据却让产物变绿，说明那个判据抓的是真问题。
- **与 AntD 的关系**：本文件是判决层，AntD 是基线。新增条款不要求"符合 AntD 的设计意图"，只要求"可测量、可复现、能红"。

### 10.1 判据上线前必须做「双点校准」

一个判据在两个**已知真值**的输入上各跑一次，两次读数都必须与人工数出来的数相等，才算能上线：

| 校准点 | 已知真值 | 用来抓什么 |
|---|---|---|
| `example-06`（应该全绿） | 每列宽度已知、8 列已知 | **误红**（判据太严或解析错） |
| `reject-01-capa-qms`（应该按 `REJECT.md` 逐条红） | 11/11 声明、`tableLayout` 缺失、33/39 折行 | **误绿**（判据看不见真缺陷）、**误红**（判据报错了对象） |

**为什么必须双点**：单点只能证明"判据跑起来了"。三次学费都是单点校准漏掉的：

| 教训 | 单点看起来 | 双点会暴露 |
|---|---|---|
| `Σ col.offsetWidth` 恒等于表宽 | 在 `example-06` 上 PASS | 在任意产物上都 PASS —— 它没有"为什么是错的"的输入 |
| `tr.offsetHeight` 含 1px 边框，阈值取 32 | 在 `example-06` 上 FAIL | `example-06` 是绿的教材，它红说明阈值在逼人删边框 |
| `float("150px")` 抛异常被吞成「未声明」 | 在 `example-06` 上 `0/8 = 0%` | `reject-01` 的人工真值是 11/11，读数 0/11 立刻对不上 |

**校准结果要写进交付表**：每个新判据一行，列 = `判据 / example-06 读数 / reject-01 读数 / 人工真值 / 是否一致`。**只要有一行"读数 ≠ 人工真值"，这个判据就不许进 CI** —— 一条读数不可信的判据，加上 CI 的自动化，等于把一个错误的结论批量生产。

### 10.2 判据的统计口径：逐页、逐条、带视口，不看总数

`reject-01` 的两个页面 FAIL 数**曾经不同（19 / 21）**，修完量具后**都是 21 条（1440 与 1600 两档合计）**，但**集合不同**：list 红在 `P15/P4/P7/P9/P10/P11/P16/P18/P19`，overdue 红在 `P1/P3a/P4/P7/P9/P10/P11/P12/P16/P18/P19`；每页每档是 `list@1440 = 10`、`list@1600 = 11`、`overdue@1440 = 11`、`overdue@1600 = 10`。

**结论比之前更硬：条数不同会骗人，条数相同也会骗人。** 任何以 `TOTAL` 或"红了几条"为口径的结论都会掩盖"哪一页红了什么"。

所以：
- 报告必须逐 `page@视口` 给「判据名 + 读数 + 红绿」，`TOTAL` 只能当索引，不能当结论；
- **先写清判的是哪一页**（判页依据 = `meta.currentPageId`），并列出「另有 N 张候选本轮未判」—— 否则"红了 10 条"没有主语；
- `--all-pages` 逐页单列计数，**不许出跨页合计**（合计会把"两页各红 21"读成"一共 42"）；
- 反样本守卫按 `page@视口` 做**集合相等**，不用「红 ≥N 条」；
- 本节所有计数（`33/39`、`11/11`、`10/11`）都必须带分母。
