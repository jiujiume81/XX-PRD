# 13 · 需求准确性的四条规则（R1–R4）

> 这份文件解决第三类问题：**样板做得像，功能就是缺**。
>
> 前两类问题已经被治过：`08` 治"形态选错"、`09` / `10` 治"行为与页面切错"。
> 但 2026-10 的 CAPA 实测暴露了另一类：产物有 7 个页面、命令策略齐、状态机也不缺，
> 而源需求里点名的**「我的任务」一次都没出现**、**「根本原因分析」没进主表**、
> **两种任务单据被合并成一张表的两种"阶段"**。校验器一条都没报 —— 因为它根本没有"该有的东西是不是都在"这类规则。
>
> **一句话**：`09` / `10` 判「写的对不对」，本文件判「**该写的写没写**」。

---

## 0. 为什么单列一份，不塞进 02

| | `02-ears-spec.md` | 本文件 |
|---|---|---|
| 粒度 | **一条**需求 | **一组**信息 |
| 问的问题 | 「这条需求写成这样会不会有歧义」 | 「源文档提到的这些东西，有多少落到了产物里」 |
| 判定时机 | 阶段② 写条目时 | R1 阶段②③；R2/R4 阶段③；R3 阶段③④ |
| 判据形态 | 句式与字段规范（人能读） | **计数闭合 + 引用解析**（脚本能算） |

三条不能塞进 `02` 的理由：

1. **`02` 管不到 R2/R4 的落点**。R2 判的是 `dataModel.relations` 与子实体状态机，R4 判的是 `capabilities[].stage` —— 这两样在阶段② 还不存在。规则写在 `02`，模型读到它时已经换了三个文件。
2. **粒度混在一份文件里会互相稀释**。`02` 现在是 213 行、专注句式；塞进 R1–R4 会到 500+ 行，且前 200 行讲"一句话怎么写"，后 300 行讲"一整个模块齐不齐"，读者会两件事都读不进去。
3. **`04-container-schema.md` 的教训**：它本来是数据契约，现在 1065 行，成了"事实上的规范核心"，所有东西都往它里面塞。**不要再造第二个。**

代价与补偿：必须在 `02` / `09` / `10` 三处各留一行指针（否则规则只对读完整个目录的模型生效）。这个代价可检（`grep -c`），比主体漂移便宜。

## 1. R1 · 字段登记：源文档点名的每个业务字段必须落到某页某区块

### 1.1 什么时候触发

**总是。** 每条需求都要过 R1。没有字段的业务（纯后台任务）在登记表里也是一条，`scope:"out"` + 理由。

### 1.2 登记表怎么写

**唯一真源**：`XX-PRD.data.json` 顶层 `fieldRegistry[]`。
**人读视图**：`shaping/field-registry.md`，由 `prd_flow.py` 从 json 渲染，文件头写死「本文件由 json 生成，禁止手改」。

```jsonc
"fieldRegistry": [
  { "id": "f-01",
    "name": "不合格（潜在不合格）陈述",
    "sourceRef": "4.7.19.1",
    "type": "longtext",
    "pageId": "page-capa-plan",
    "block": "n-card-statement",
    "required": true,
    "scope": "in",
    "oneToMany": false },
  { "id": "f-07",
    "name": "不合格（潜在）根本原因分析（5why分析法）",
    "sourceRef": "4.7.19.3",
    "type": "longtext+attachment",
    "pageId": "page-capa-plan",
    "block": "n-card-root-cause",
    "required": true,
    "scope": "in",
    "oneToMany": false },
  { "id": "f-12",
    "name": "我的任务（各负责人待办入口）",
    "sourceRef": "4.7.19.2 + 4.7.19.3",
    "type": "page",
    "pageId": "page-my-tasks",
    "block": "n-table-my-tasks",
    "required": true,
    "scope": "in",
    "oneToMany": false }
]
```

### 1.3 字段定义

| 字段 | 必填 | 取值 | 说明 |
|---|---|---|---|
| `id` | ✓ | `f-NN` | 全局唯一、不复用 |
| `name` | ✓ | 文本 | **逐字取自源文档**，不许改写、不许归纳。改写会导致 R1-b 匹配失败 |
| `sourceRef` | ✓ | 条目号 | 如 `4.7.19.3`；同一字段来自多处用 `+` 连接 |
| `type` | ✓ | `text` \| `number` \| `date` \| `enum` \| `longtext` \| `attachment` \| `longtext+attachment` \| `ref` \| `page` | `page` 表示"结构性功能"（如「我的任务」），它不是一个字段而是一个页面 |
| `pageId` | ✓ | `pages[].id` | 落位页面 |
| `block` | ✓ | 组件树节点 id | 落位区块。`type:"page"` 时可写该页的表格/主容器节点 |
| `required` | ✓ | bool | 源文档写"必须/需/应录入"→ true |
| `scope` | ✓ | `in` \| `out` | `out` 必须给 `reason` + `decisionId` |
| `reason` | 条件 | 文本 | `scope:"out"` 必填 |
| `decisionId` | 条件 | `D-NN` | `scope:"out"` 必填，指向 `decisions.json` 的一条 |
| `oneToMany` | ✓ | bool | 见 R2 |

### 1.4 `source-terms.json`：点名词清单怎么来

阶段② 落盘 `shaping/source-terms.json`：

```jsonc
[{ "term": "根本原因分析", "sourceRef": "4.7.19.3", "raw": "需录入不合格（潜在）根本原因分析（5why分析法）" }]
```

**两级来源，任取其一（2026-10-27 补）**：

| 位置 | 什么时候用 | 谁读 |
|---|---|---|
| 产物顶层 `sourceTerms[]`（字符串数组） | **交付包 / 单文件示例**：`shaping/` 不随产物走，只带一个 `.data.json` 时用它 | `validate_prd_json.py` 优先读这个 |
| `<产物目录>/shaping/source-terms.json` | 完整工作区：阶段② 的原始落盘位置 | 同上，内联不存在时读它 |

> **为什么允许内联**：交付物是单文件，`shaping/` 不会被带走。若只认外部文件，那么任何**交付包**
> 在 R1-c 上永远 `INCOMPLETE` —— 判据在交付现场失效，等于没写。
>
> **两处都没有时不许判 PASS**：分母为 0 时「登记数 ≥ 0」恒成立，那是恒真式。此时报 `INCOMPLETE`。

**抽取规则**（给模型看的，不是给脚本判的）：

1. 引号 / 书名号 / 括号里的名词短语：`「…」`、`“…”`、`**…**`、`（…分析法）`
2. 录入类动词的宾语：`录入 X` / `记录 X` / `上传 X` / `维护 X` / `确认 X` / `选择 X` / `分发至 X`
3. 原文里被加粗的整句，至少要抽出它的核心名词

**判定不靠这条规则，靠计数**：`fieldRegistry.length ≥ sourceTerms.length`。

> 人可以往清单里加条目，**但不能删** —— 删等于删证据。
> 真要不做，写 `scope:"out"` + 理由 + 决策 id，让它留在表里可见。

### 1.5 四条机检（全 ERROR，两个 profile 同）

| # | 判据 | 红的样子 |
|---|---|---|
| **R1-a** 悬空落位 | `pageId` 在 `pages[]` 里，`block` 在该页 `componentTree`（或该页 `interactions` 的 `on.target`）里 | `f-07 的落位 n-card-root-cause 在 page-capa-plan 里不存在` |
| **R1-b** 落位可见 | `block` 节点的**可渲染文本**里能匹配 `name` 去掉括注后的核心词。可渲染文本 = 该节点 `props` 的 `text`/`title`/`label`/`content`/`placeholder`/`extra`/`value`/`description`/`detailTitle` + `props.columns[].title` + `children` 里的裸字符串 | `f-07 登记了区块，但该区块文本里找不到「根本原因分析」` |
| **R1-c** 计数闭合 | `fieldRegistry.length ≥ source-terms.json.length` | `源文档点名 14 项，登记 11 项，缺：责任部门确认纳期 / 我的任务 / …` |
| **R1-d** 反向覆盖 | `scope:"out"` 必须有非空 `reason` 且 `decisionId` 指向存在的决策 | `f-14 scope=out 但无 decisionId` |

### 1.6 造红（必须能复现）

| 造红动作 | 应红在 |
|---|---|
| 把 `example-06` 某条 `block` 改成 `n-不存在` | R1-a |
| 把某条 `scope:"out"` 的 `reason` 清空 | R1-d |
| 删掉 `fieldRegistry` 全部条目 | R1-c（`源点名 N 项，登记 0 项`） |
| 把 `block` 指向一个空 `Div` | R1-b |

### 1.7 三个反模式

| # | 反模式 | 为什么错 | 怎么改 |
|---|---|---|---|
| 1 | **用"正文提到过"当落位证据** | 证据 §3.2 已经证伪：`根本原因` 在 CAPA 产物里命中 1 次，而那 1 次在**测试数据的值**里，主表根本没有这个字段 | 只认 `block` 节点里的可渲染文本 |
| 2 | **登记表写成字段字典**（把源文档每个名词都灌进去） | `R1-c` 能过，但 `R1-b` 大面积 ERROR，最后靠"降低匹配标准"过关 | 只收"要落到界面上给用户看/填的"，纯后台字段写 `scope:"out"` |
| 3 | **`type:"page"` 滥用**（什么都登记成页面） | 页面级登记逃过 `block` 可见性检查（页面总"存在"） | `type:"page"` 只给结构性功能（「我的任务」这种），且必须仍有 `block` 指向该页主容器 |

## 2. R2 · 一对多结构判定

### 2.1 什么时候触发：触发词表

源文档出现下列任一词，即命中一次（同一句里出现多个词只计一次）：

| 类别 | 触发词 |
|---|---|
| **分派类** | 分发至、分发到、分派、指派、下发、派给 |
| **复数类** | 各（各负责人 / 各部门）、每个、分别、逐一、逐条、多个、若干、多条、一组 |
| **明细类** | 明细、子项、子任务、措施项、任务行、清单项、逐项 |
| **拆分类** | 拆成、分为、分成…类、两种、两类 |

**命中数必须等于 `fieldRegistry` 里带 `oneToMany` 裁决的条目数。** 少一条 → ERROR。

### 2.2 判定：三个条件同时成立才建主子结构

**不是见词就建表。** 满足以下三条 → `oneToMany: true`：

- **(a) 实例数 > 1**：同一主记录下会有多条（一张 CAPA 单下有多条纠正任务、多条系统性措施）；
- **(b) 有自己的状态**：子实体状态不是主实体状态的投影（「待执行 / 待验证」不能由「待分析 / 待关闭」推出）；
- **(c) 有自己的操作人**：负责人 / 责任人，可以与主实体操作人不同。

**缺任一条 → `oneToMany: false` 并写明缺哪条**（写在 `reason`）：

```jsonc
{ "id": "f-20", "name": "检验项", "oneToMany": false,
  "reason": "缺 (b)：检验项状态由主任务状态单向投影，没有独立流转" }
```

### 2.3 `oneToMany: true` 的四条硬要求

| # | 要求 | 判据 |
|---|---|---|
| **R2-a** 关系声明 | `dataModel.relations[]` 有一条 `{from: 主实体, to: 子实体, kind: "1:N"}` | 查不到 → ERROR |
| **R2-b** 独立状态机 | `stateMachines[]` 里有 `entity === 子实体` 的一条，状态数 ≥3，且**其状态集合不是父状态机的子集** | 是子集 → ERROR「子实体状态是主状态的投影，不需要独立状态机」 |
| **R2-c** 独立操作人 | 子实体至少有 1 条 `capability`，其 `actor` 与主实体提交命令的 `actor` **不同** | 全同 → ERROR |
| **R2-d** 不合并 | 子表（`MasterDetail.children[1]` 或子表节点）的 `columns[]` 里**不得**出现 `阶段` / `类型` / `stage` 列 | 出现 → ERROR「两类单据被合并成一张表的两种阶段」 |

### 2.4 为什么 R2-d 是本文件最硬的一条

CAPA 产物把「纠正任务」与「系统性措施」合并成一张 8 列子表，用 `阶段` 列区分（证据 §3.1 结构事实）。这个做法**看起来更整齐**，所以特别容易被选中。它错在：

- 两种单据**字段不同**（纠正：纠正/负责人/纳期；系统性：措施/责任人/纳期 + 附带根因分析与附件）；
- 两种单据**状态不同**（纠正中→待验证→已完成；执行中→待验证→待关闭）；
- 合并后**用户无法回答"这条措施现在在哪个环节"** —— 因为"环节"被降级成了一个列值，而列的排序/筛选/状态机都不认它。

### 2.5 造红

| 造红动作 | 应红在 |
|---|---|
| `source-terms` 里加一条含「分发至各负责人」的原文，登记表不加裁决 | 计数不闭合（命中 1、裁决 0） |
| 把 `oneToMany: true` 的子实体状态机删掉 | R2-b |
| 在子表 `columns` 里加一个 `阶段` 列 | R2-d |
| 把 `oneToMany` 改成 `false` 但 `reason` 空 | 裁决无效（视同未裁决） |

### 2.6 反模式

| # | 反模式 | 为什么错 |
|---|---|---|
| 1 | 用"有没有 `MasterDetail` 组件"当 R2 判据 | 组件存在 ≠ 语义正确：CAPA 有子表，但合并了两类任务，组件判据会放过它 |
| 2 | "满足任一条就建主子表" | 会造成每个列表页都被要求建主子表（`各`、`分别` 在中文里太常见） |
| 3 | 用 `阶段` 列区分两类单据 | 见 §2.4 |

## 3. R3 · 角色任务归属：每个有命令的角色必须有待办入口

### 3.1 判据

对 `users[]` 里**每一个** role `r`：

> 若 `r` 出现在**任一** `capabilities[].actor` 中，则必须存在至少一个页面 `p`，满足：
> 1. `p.contract.actor` 含 `r`；
> 2. `p` 在 `tasks[]` 里对应一条 `task`，且 `task.actor` 含 `r`；
> 3. `p` 有入口：`p.entryFrom` 非空，**或** `p` 是初始页 / 导航根节点。
>    （字段在**页面顶层**，不是 `contract.entryFrom` —— `contract` 只承载 `actor` / `owns` / `doneWhen`。
>    2026-10-27 修正：v1 写 `p.contract.entryFrom`，而 `example-05` / CAPA 两个产物的入口都写在
>    `pages[].entryFrom`，`contract.entryFrom` 逐页为 `None` —— 按原文实现会把每一页都判成「无入口」，
>    包括教材。这是字段名写错，不是阈值问题。）

任一不满足 → **ERROR**，输出形如：

```
R3 角色待办覆盖：u-qa ✓ / u-dept ✗ / u-manager ✓ (2/3)
  u-dept 有 3 条命令（cap-correct-submit, cap-systemic-submit, cap-systemic-execute），
  但没有任何页面以它为 contract.actor 且能被它进入。
```

### 3.2 追加一条：有 `submit` 的角色必须有「待办」性质页面

若某 role 的 capability 中有一条 `stage: "submit"`（见 R4），则该 role 必须有页面满足：`contract.owns` 含该 submit 命令，且 `contract.doneWhen` 描述了"提交完成"。

**不看页面名。** 页面叫「我的任务」「待办」还是「执行台」都不影响判定 —— 文字判据改个名就绿。

### 3.3 「我的任务」的形态：**Owner 已裁定为独立页面**（2026-10-27）

> **来源变了。** 本节 v1 版是「显式默认项」，理由是源需求只写「需具备类似『我的任务』的功能」、没说形态。
> 2026-10-27 Owner 明确表态：**「我的任务这类型功能应该是独立窗口」**。自此这条**不再是默认值，而是有来源的需求**
> （H1 反馈，Owner 本人在评审中提出）—— 按本文件 §0 的口径，它现在可以、且必须被判定。

**裁定形态**：

```
独立页面（pages[] 里的一条）+ 导航入口
   → 该 role 从导航进得去、进去只看到自己的活、能做完并提交
   → 不是：工作台卡片 / 别人页面上的 Tab / 抽屉 / 「从别人的单据页借道」
```

**为什么原来那三条理由不成立**（逐条回应；原文保留在下方，方便复核）：

| 原理由 | 为什么不成立 |
|---|---|
| 待办的价值在聚合不在浏览 | 聚合与独立页**不互斥**：独立页第一屏照样可以是「我的待办 n 条 + 按紧急度排序」。原判断把「不做一张可筛选的大表」错当成了「不做独立页」——这是把一个**交互取舍**当成了**形态结论** |
| 独立页会产生两处入口、两套筛选 | 两套筛选来自**重复定义**，不来自「有独立页」。用「两处引用同一 `viewId`」即可消除（约束 1/3 原样保留）。而且它推不出「不要独立页」，只能推出「两处不许各写一套」 |
| R3 判的是「有没有地方干活」，不是「有没有叫我的任务的页」 | 这条把**判据的下限当成了需求的上限**。CAPA 的 `u-dept` 正是反证：他从质量部详情页「借道」也能提交，按 R3 判为过，但整份产物里**没有一处只看他自己活的入口**。判据能过 ≠ 需求满足 |

**四条约束（缺一条，独立页就退化成「又一个列表页」）**：

| # | 约束 | 机检口 |
|---|---|---|
| 1 | 独立页的视图与该 role 的待办**同源**：导航角标 / 汇总数引用同一 `viewId` | 两处各写一套筛选 → ERROR |
| 2 | 该页 `contract.actor` 含该 role，`contract.doneWhen` 描述「提交完成」 | 与 §3.2 同款 |
| 3 | 该页 `contract.owns` **覆盖该 role 的全部提交类命令** | 缺一条 → ERROR（**前置条件见下**） |
| 4 | 该页在导航里可达：`p.entryFrom` 非空，**或**它是根页 | 与 §3.1 第 3 条同款 |

**约束 3 的取数口径（2026-10-27 已实现为 `R3-b`）**：判「提交类命令」靠 `capabilities[].stage`，
而它在**现有全部产物里都是 `null`**（`example-05` 十项、`CAPA` 十六项实测）。没有 `stage` 就只剩
「命令名里含不含 `submit`」这一条路，那是 §3.2 明令禁止的文字判据 —— 所以实现里遇到 stage 全空时
报 **`INCOMPLETE`（判不了）**，不报 PASS、也不报 ERROR。**这条判据不会因为「大家都还没写 stage」
就悄悄算通过**；它只是暂时没有输入，而 `INCOMPLETE` 在 `--require-r` 下与非 0 退出等价。

**原 v1 默认形态（已作废，保留以便复核）**：

```
工作台「待办」卡片（聚合该角色的待办条数）
   + 「我的任务」导航入口 → 指向**筛选后的同一张列表**
   → 不新增独立列表页
```

**Owner 若要再改回去**：删掉独立页、卡片改 `navigate` 指向筛选后的列表。**改的是产物，不是本节的判据** ——
判据从头到尾只要求「独立页 + 可达 + 覆盖提交命令」，它不关心页面叫什么、放在导航第几项。

### 3.4 为什么这条是本轮的重点之一

CAPA 产物里 `u-dept`（部门负责人）在 `capabilities` 里有提交执行结果的命令，但 7 个页面里**没有任何一个是他能进入做事的入口**。他只能从质量部的详情页"借道"操作。

这不是"少画一个页面"，是**少了一个角色的完整任务闭环**：他有活要干，但没有地方干。用户说「并需具备类似『我的任务』的功能」—— 这句话在 v1 里没有任何检查点：它既不是一条 EARS 需求（没有触发条件）、也不是一个组件，也不被 `validate_prd_json` 任何规则覆盖。**2026-10-27 起它有了**：R3-b 判「有提交命令的角色有没有独立待办页」，且 Owner 已裁定形态为独立页面。但判据**尚未实现**（`XX-041`），所以此刻它仍是「写了没人判」—— 这一点必须写在交付说明里，不许因为条文已改就宣称已解决。

### 3.5 造红

| 造红动作 | 应红在 |
|---|---|
| 从 `example-05` 删掉某个非 system role 的主页面 | R3（该 role 有 capability 但无页面） |
| 把某页 `contract.actor` 里的 role 删掉 | R3（若该 role 无其他页面） |
| 把某页 `entryFrom` 清空且它不是根节点 | R3 第 3 条 |
| 把某 role 的独立待办页删掉，只保留他从别的页「借道」的提交能力 | §3.3 约束 3。**注意：这个动作按旧 R3 判为「过」** —— CAPA 的 `u-dept` 正是这个状态。所以它不是 R3 的造红，是「R3 不够用」的证据。当前无法机检（前置缺 `stage`），故本轮只作人工造红记录 |
| 把独立页与导航角标的 `viewId` 改成两个不同值 | §3.3 约束 1（机检口已写，但同为待接线） |

### 3.6 反模式

| # | 反模式 | 为什么错 |
|---|---|---|
| 1 | 页面名含"我的"就判通过 | 文案判据，改个名就绿 |

| 4 | **把 §3.3 的形态写成「源文档要求」** | 源文档只写「类似『我的任务』的功能」，**形态来自 Owner 2026-10-27 的表态**。引用时必须写「Owner 裁定」，不写「源需求原文」—— 两者都能被推翻，但推翻方式不同：前者要 Owner 自己改口，后者要改原始文档。而且按 v1 的旧默认形态（工作台卡片）写进产物，Owner 一看就会连 R3 一起质疑 |

## 4. R4 · 执行 / 验证双环节

### 4.1 适用范围

对每个「措施 / 任务」类实体 `E`，判定方式：**`E` 是任意 `relations[].kind === "1:N"` 里的 `to`**。

### 4.2 新增字段

`capabilities[].stage`，枚举 **两个值**：

| 值 | 含义 | 必须满足 |
|---|---|---|
| `submit` | 执行人提交执行结果 | `guard` 里写明佐证要求（如"佐证已上传"）；`to` = 待验证 |
| `verify` | 验收人出结论 | `guard` 里写明结论项完整；`to` = 已完成 / 待关闭 |

不加第三个值。不是每个 capability 都要有 `stage` —— 只有"措施/任务"实体的提交与验收动作需要。

### 4.3 四条判据

| # | 判据 | 档 |
|---|---|---|
| **R4-a** 齐全 | `E` 至少有 1 条 `stage:"submit"` 和 1 条 `stage:"verify"`，`entity` 都是 `E` | ERROR |
| **R4-b** 角色不同 | `submit.actor ∩ verify.actor === ∅` | ERROR |
| **R4-c** 状态衔接 | `verify.from` 必须包含 `submit.to` | ERROR |
| **R4-d** 主单据联动 | `verify` 生效后有 `effects[]` 指向主实体，或状态机里有 `parentEffect` 写明主状态变化 | WARN（默认）/ ERROR（delivery） |

### 4.4 R4-b 的例外（必须显式申请）

业务上确实存在"一人双角色"（小团队里质量部兼执行）。此时必须写：

```jsonc
{ "id": "cap-sys-verify", "stage": "verify", "actor": ["u-qa"],
  "sameActorOk": true,
  "reason": "本单质量部同时是责任部门；四眼原则由上级抽样复核替代（cap-sys-audit）" }
```

`sameActorOk: true` 但没有 `reason` → ERROR。`reason` 里必须写出"四眼原则怎么被替代满足"，只写"人员不足"不算。

### 4.5 为什么这条不能省

源需求 4.7.19.2 原文：「负责人记录执行情况 + 上传佐证 → 提交后进入纠正验证环节，任务状态『待验证』」；4.7.19.3：「质量管理部验收，记录验收情况 + 佐证 → 『已完成』」。

**两个角色、两个环节、两次提交、两份佐证。** 产物把它们压成一个「状态」列，等于让 `佐证` 与 `验证意见` 抢同一个抽屉，且"谁验的"无法追溯。这在质量体系里是实质性缺陷 —— 不是排版问题。

### 4.6 造红

| 造红动作 | 应红在 |
|---|---|
| 删掉 `stage:"verify"` 的那条 capability | R4-a |
| 把 `verify` 的 `actor` 改成与 `submit` 相同 | R4-b |
| 把 `verify.from` 改成 `["已提交"]`（`submit.to` 是 `待验证`） | R4-c |
| 加 `sameActorOk: true` 但不写 `reason` | R4-b（例外无效） |

### 4.7 反模式

| # | 反模式 | 为什么错 |
|---|---|---|
| 1 | 用"状态名里含『验证』"当判据 | 那是状态机判据，不能证明有第二个角色的按钮 |
| 2 | `stage` 写成自由文本（`"submit"` / `"提交"` / `"exec"` 混用） | 枚举只有两个值，多一个都算错 |
| 3 | 默认允许同一人执行+验证 | 四眼原则必须是默认；例外要显式申请并给替代方案 |

## 5. 机检总表

| 规则 | 判据 | 形态 | 档 | 落点 |
|---|---|---|---|---|
| R1-a | 悬空 `block` / `pageId` | 引用解析 | ERROR | `validate_prd_json.py` |
| R1-b | 落位区块文本不含字段核心词 | 文本匹配 | ERROR | 同上 |
| R1-c | 登记数 < 点名词数 | 计数闭合 | ERROR | 同上 |
| R1-d | `scope:"out"` 缺理由或决策 | 字段完整性 | ERROR | 同上 |
| R2 | 触发词命中数 ≠ `oneToMany` 裁决数 | 计数闭合 | ERROR | 同上（读 `source-terms.json`） |
| R2-a | 缺 `kind:"1:N"` 关系 | 引用解析 | ERROR | 同上 |
| R2-b | 子实体状态集合 ⊆ 父状态集合 | 集合比较 | ERROR | 同上 |
| R2-c | 子实体无独立操作人 | 集合比较 | ERROR | 同上 |
| R2-d | 子表出现 `阶段` / `类型` / `stage` 列 | 列名匹配 | ERROR | 同上 |
| R3 | 有 capability 的 role 无页面 | 集合覆盖 | ERROR | 同上 |
| R3-b | 有提交命令的 role **无独立待办页**（只有「借道」入口） | 集合覆盖 + 页面可达 | ERROR（**前置**：`capabilities[].stage` 有值，否则「提交类」无定义） | 同上 |
| R4-a | 缺 `submit` 或 `verify` | 存在性 | ERROR | 同上 |
| R4-b | `submit.actor ∩ verify.actor ≠ ∅` | 集合交集 | ERROR | 同上 |
| R4-c | `verify.from` 不含 `submit.to` | 包含判定 | ERROR | 同上 |
| R4-d | 无主单据联动 | 引用解析 | WARN / ERROR | 同上 |

**全部 15 条判定都在 `validate_prd_json.py` 一处实现。** 不在生成器、检查器里各写一遍 —— 一旦各长一套，"什么算一对多""什么算独立状态"会在两个检查里给出不同答案，而且是"两边都 PASS、口径不同"的静默分叉，比报错难查得多（`09` §2.4 已经为"什么算系统行为"付过这个学费）。

> **落地状态（2026-10-27 更新）**：这 15 条**已全部实现**在 `scripts/validate_prd_json.py` 的
> `validate()` 第 12 节，三态分开输出：`PASS` / `ERROR` / `INCOMPLETE`。
> 逐条造红由 `tests/check_r1_r4.py` 保证（15 个单点变体），绿样本是
> `tests/fixtures/fixture-r1-r4.json`；两者一起进了发布门 **DoD 12**（`check_release.py`）——
> 只写判据不进闸门，与「规则写了但页面没落地」同型的病。
>
> **`INCOMPLETE` 是第三种状态，不许并进 PASS 或 ERROR**：它表示「判据在，产物里没有可判的输入」。
> 并进 PASS 会得到全绿的假象；并进 ERROR 会把「没写」和「写错」混成一件事（处置相反：前者补数据，
> 后者改数据）。它默认**不**让退出码非 0（存量产物写于本规则之前，一次全红只会让人关掉检查），
> **但 `--require-r` 下与非 0 等价** —— 真正要求 R 组合格的场景用后者的语义。
>
> **实测读点（2026-10-27，`reject-01-capa-qms` 反样本）**：
> `R 组：判定 15 条 → PASS=0 / ERROR=2 / INCOMPLETE=13`。两条红是：
> - `R2-d` `page-capa-list` 的子表出现「阶段」列 —— 与 §2.4 说的「两类单据被合并成一张表」吻合；
> - `R3` `u-executor` 有命令但没有一个页面以他为主体且能进入 —— 与 §3.4 完全一致。
>
> **这两条就是人工评审当初指出的缺陷**，新判据在真实现场上把它们抓了出来（不是靠造红）。
>
> **剩余缺口（如实记）**：CAPA 的 `R1` / `R4` 仍为 `INCOMPLETE`，因为它没有 `fieldRegistry`、
> 没有 `dataModel.relations`、`capabilities[].stage` 全空 —— 所以 `XX-041` 验收第 1 条要求的
> 「R1 ≥2 / R2 ≥2 / R3 =1 / R4 ≥2 条 ERROR」目前只达成 **R2-d + R3**，其余要靠给反样本补数据，
> 不能用「判据已实现」代替。
>
> 与此对照：`12` 的视觉条款全部依赖渲染实测，`validate_prd_json.py` **永远**判不了，所以 `12` 里
> 一个 `ERROR` 都不许有（`12` 速查表上方的执行者说明）。
>
> **实现时发现的两处坑（已修，留档免得重踩）**：
> ① `p.contract.entryFrom` 是错字段 —— 入口在 `pages[].entryFrom`（见 §3.1 第 3 条的修正）。
> ② R2-d 的子表列在**节点级 `children[1].props.columns`** 里；早期版本写成 `props.children`，
> 后者是 I-07 之前的老写法，按它实现会让这条判据恒 PASS（永远找不到列，也就永远不红）。

## 6. 与 `09` / `10` 的边界（不重复的部分）

| 问题 | 归谁 |
|---|---|
| 「这个按钮在哪些状态可点」 | `09`（`capabilities[].from` / `policy` / `reason`） |
| 「这个页面该不该和那个页面合并」 | `10`（合并五判据 / 拆分七信号） |
| 「这条命令该由哪个页面发起」 | `10`（`contract.owns`） |
| **「源文档说的这个字段有没有地方落」** | **本文件 R1** |
| **「一对多该不该拆成主子结构」** | **本文件 R2** |
| **「这个角色有没有地方干活」** | **本文件 R3**（含「有没有一处只看到他自己的活的独立页」，R3-b） |
| **「执行和验证是不是两个角色」** | **本文件 R4** |

一条给 `10` 的拆分信号（**已由 §3.3 升格为判据 R3-b，不再是建议**）：**角色缺独立待办入口** —— 某角色有 capability、也能从别处「借道」提交，但没有任何页面以他为主体、只显示他自己的活，此时应**新增一个独立页面**（而不是把他塞进别人的页面）。CAPA 的 `u-dept` 就是这一状态。
